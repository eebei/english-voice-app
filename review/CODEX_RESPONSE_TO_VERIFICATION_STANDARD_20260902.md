## 2. §5のLLM意図分類案への反証

LLMに数値を持たせず「質問の軸だけ」を分類させる案は、正規表現の軸取り違えを減らす可能性がある。一方で、次の悪化リスクがある。

1. **分類自体の誤り**: STT誤認、短い相槌、複数質問、否定・皮肉・途中発話を誤分類する。分類結果を正しいものとしてローカル計算へ渡すと、誤った事実を高速に返す。
2. **レイテンシと可用性**: 毎回LLMを呼ぶと、現在のローカル処理より遅くなり、ネットワーク障害時に事実回答まで失う。レース中の反射・単純事実には不適切。
3. **コスト逆転**: 短い分類でも全質問でAPIを呼べば、現行のLLM回答を短くしただけになり、想定したコスト削減が実現しない可能性がある。
4. **フォールバックの危険**: 分類タイムアウト時に旧正規表現へ戻すと、同じ誤分類が再発する。安全なfallbackは「質問軸不明としてLunaへ会話処理」または「確定済み反射・事実だけ継続」である。
5. **質問と命令の境界**: 「この周で入るよ、可能？」のような決定＋相談を単一軸へ潰すと、ピット実行・戦略相談のどちらかを失う。分類結果は単一ラベルでなく、`speech_act`と`fact_axis`の分離が必要。

## 3. `confidence`契約の修正方針

返信文やintent名から確度を推測する実装は、今回の7件のように再び抜ける。Codexの先行修正（`39a4386`、`9e8e904`）で不整合は検出・修正したが、文字列判定は最終形ではない。

推奨する契約は、回答生成前に構造化すること。

```js
fact({ axis: 'gap_behind', value: 4.0, unit: 's',
  source: 'irsdk', observed_at: 123, target_car_idx: 7,
  validity: 'fresh', confidence: 'confirmed' })

unavailable({ axis: 'leader_gap', reason: 'no_authoritative_value',
  next_action: 'wait_for_next_snapshot' })
```

要件:

- `fact()`は値・単位・出所・観測時刻・対象・有効性を必須にする
- 1項目でも欠ければ`fact()`を生成しない
- `unavailable()`は値を持てない。0や空文字を許可しない
- `estimated`は推定根拠と確度を必須にする
- 発話層は構造体だけを受け取り、事実値を書き換えられない
- rendererは`source`と`validity`を検査し、LLM回答で上書きしない

現行の文字列ベース確度判定は暫定的な検査用として残してよいが、V4採用条件にはしない。

### 6-3. `disputed()` 契約

`fact()`／`estimated()`／`unavailable()`に加え、`disputed()`を導入する。

```js
disputed({
  axis: 'gap_behind',
  previous_fact_id: 'gap|behind|session|generation',
  driver_observation: '後ろ2.0だね',
  status: 'held',
  next_action: 'wait_for_new_observation',
  memory_policy: 'candidate_until_confirmed'
})
```

契約上の必須動作は次の通り。

1. 直前に発話した事実をイベント単位で保留する
2. ドライバーの自由文を新しい数値として自動採用しない
3. 同一イベントの再発話と戦略計算への利用を止める
4. 次の観測で対象車・世代・時刻が更新されたら再評価する
5. 再観測が一致すれば`fact()`へ昇格し、不一致なら保留を継続する
6. 訂正内容は記憶候補として保存し、合意なしに恒久的事実へしない
7. Lunaは「その値は保留にする。次の計測で言い直す」と自然に返す

### 公開判断

Build 292の既存artifactには、この完全な`disputed()`契約と17件の訂正入口拡張は含まれていない。したがって、これらを実装・実行テスト・実走再生で確認するまでは、訂正対応を理由にBuild 292を「完成」と扱わない。

**訂正の受領を最初に言う**ことを契約側で必須にしたい。
