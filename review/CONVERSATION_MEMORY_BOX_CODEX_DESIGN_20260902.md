# 会話記憶ボックス — Codex設計 v1

作成: 2026-09-02 JST  
設計: Codex / 反証・実装: Claude Code / 決裁: Yuji  
正本依頼: `review/CONVERSATION_MEMORY_BOX_DESIGN_REQUEST_20260902.md`

## 設計目標

Lunaの会話を毎ターン独立した質問応答にせず、同一セッション内の直前の発話、未解決の訂正、約束、判断を次の発話へ接続する。ただし、履歴中の古い数値を現在の事実として再利用しない。

合格条件は、8/30〜9/2の実走ログ再生で、訂正16件をすべて `disputed()` 経路へ到達させ、受領・訂正後の扱い・次回回答への反映をtraceで確認できること。

## 1. 設置場所

### 正本

Electron rendererのユーザーPC内ストレージに置く。既存の`pw_raceHistory`等と同じユーザー領域を使い、初期実装で新しいサーバー永続化を必須にしない。

### Chief Mode

複数PC・ドライバー交代時だけ、許可された構造化要約をサーバーへ同期する。生の会話全文、音声、未確認数値は同期しない。同期レコードには`user_id`、`session_id`、`source_device_id`、`revision`を付け、古い端末が新しい正本を上書きできないようにする。

## 2. 箱の粒度

- `session_key = user_id + session_id + session_type + track + car`
- Practice / Qualify / Raceを別セッションとして保持
- セッション内はturn単位で順序を保持
- 耐久のドライバー交代は同一event配下の別sessionとして関連付ける

保存階層は次の3つとする。

1. **短期turns**：直近30分または直近60 turn
2. **未解決項目**：訂正・約束・質問待ち
3. **長期要約**：終了時に抽出した判断・結果・次回への注意点

## 3. `open_items` 状態機械

```text
open
  ├─ acknowledged → resolved
  ├─ acknowledged → corrected → resolved
  ├─ held → resolved
  └─ expired
```

各項目は`item_id`、`axis`、`source_turn_id`、`observed_value`、`corrected_value`、`status`、`updated_at`を持つ。

- `open`：訂正・質問・約束が未処理
- `acknowledged`：Lunaが受領を明示した
- `held`：データ待ち。次の取得で再評価する
- `corrected`：ドライバー訂正を新しい候補として受理した
- `resolved`：検証または再回答で閉じた
- `expired`：セッション終了・対象イベント失効で利用禁止

`disputed()`は、ドライバー訂正を受けた時に必ず生成する。`fact()`や`unavailable()`で代用しない。訂正受領の発話は「わかった、今の値は訂正して扱うね」のように短く返し、単なる「了解」で終了させない。

## 4. 反射コールと会話履歴の境界

停止車両、黄旗、左右の車などの反射コールは、会話履歴の`turns`には入れない。ただし別の`race_timeline`へ、発生時刻・種別・対象・発話結果・訂正の有無を保存する。

同一内容の反射が短時間に連続した場合は1件へ集約する。会話ボックスへ入れるのは、ドライバーが反射について質問・訂正した場合だけとする。

## 5. 要約のタイミングと粒度

- レース中：直近30分のturnsのみLLM文脈へ投入
- 重要な`disputed`、pit decision、strategy decision、driver constraintは即時に構造化保存
- セッション終了：生発話をそのまま引用せず、最大5項目の要約へ蒸留
- 次回開始：同一user / track / car / formatの長期要約を最大3件だけ取得

長期要約へ保存するのは「判断・根拠・結果・次回の条件」。ドライバーの発話全文や古いGAP数値は保存しても、現在値として回答へ使わない。

## 6. 既存モジュールとの関係

会話記憶ボックスは既存5モジュールの置換ではなく、短期会話を束ねる上位層として追加する。

```text
session-memory       → セッション事実・過去走行
decision-memory      → 戦略判断と結果
luna-self-memory     → Lunaの自己訂正・反省
memory-action-layer  → 保存・取得アクション
pddp                 → ドライバー改善結果
        ↓
conversation-memory-box → turns / open_items / timeline / summary
        ↓
intent → authoritative fact → response → radio delivery → outcome
```

数値の権威は既存のBridge / local fact engineに残す。会話ボックスは数値を決めず、発話の連続性と訂正状態だけを提供する。

## 7. 入口→出口の必須trace

```text
driver_turn
 → classified_intent
 → memory_context_loaded
 → fact_or_dispute_attached
 → response_built
 → queued
 → speech_started
 → speech_completed / aborted
 → open_item_updated
```

どの段階で止まっても、`request_id`単位で理由を記録する。内部保存だけ、LLM応答だけ、TTS生成だけでは成功と扱わない。

## 8. Claude Codeへの反証依頼

1. `localStorage`だけではChief Mode・複数PCで競合しないか。
2. 直近30分／60 turnがトークン・レイテンシ・費用上限を超えないか。
3. `disputed()`受領が既存の`unavailable()`・driver command・radio priorityと衝突しないか。
4. 反射コールを履歴から除外しても、訂正・デブリーフ・結果採点が欠落しないか。
5. 既存5モジュールとの二重保存、古いidentity、session境界漏れがないか。
6. 8/30〜9/2の実走ログ再生で訂正16件を一件ずつ通せるか。

反証で問題が出た場合は、実装を始めず本書へ差戻し理由と測定値を追記する。commit / push / build / deploy / 公開はYujiの明示GOまで行わない。

## ❌ 落ちる3件 — §4「反射コールは turns に入れない」が原因

設計 §4：

> 停止車両、黄旗、左右の車などの反射コールは、会話履歴の `turns` には入れない。
> 会話ボックスへ入れるのは、**ドライバーが反射について質問・訂正した場合だけ**とする。

**この条件は循環している。** ドライバーの発話が「反射への訂正」だと判定するには、
**直前の反射コールが文脈に無ければならない**。しかし設計はそれを `turns` から除外する。
**除外された対象への訂正は、訂正だと分からない。**

実データで3件該当する。

| # | Luna（反射） | ドライバー | 現行の処理 |
|---|---|---|---|
| 18 | **右に車。** | ハマってた。車はコールしてなかったね。今 | `conversation`（LLM） |
| 27 | 次のラップは白紙。リセットしよ。**左に車。** | 左はウォールしかないです。 | `conversation`（LLM） |
| 30 | わかった。…**左に車。** | 左全然車いないです。 | `conversation`（LLM） |

**16件中3件（19%）が反射コールへの訂正である。** そして内容が重い。
27・30 は「左に車」が**誤検知だった**という指摘であり、
18 は「**コールすべき車をコールしなかった**」という指摘である。
**安全コールの精度に対する唯一のフィードバック経路**がここにある。

### 提案（差戻し案）

反射コールを `turns` から**除外しない**。ただし2点で膨張を抑える。

1. **直近N件だけ**（例：直近5件・120秒以内）を `turns` へ入れる。
   8/31 のサイド20回のような連呼は、設計 §4 の「同一内容の短時間連続は1件へ集約」をそのまま適用する
2. `race_timeline` は設計どおり別に持つ。**両方持つ**（timeline は全件、turns は直近のみ）

`turns` に入れないのではなく、**入れる量を絞る**のが正しい。
「左に車」が文脈に無ければ、「左は壁しかない」はただの独り言にしかならない。

# Codex再設計 v2（2026-09-02）

## v2で変更する契約

### A. 反射コールは「完全除外」しない

- `race_timeline`には全反射イベントを保存する。
- 会話ボックスの短期文脈には、直近120秒かつ最大5件の反射イベントを入れる。
- 同一種別・同一方向・同一対象の連続イベントは1件へ集約する。
- 安全反射の発話優先度・即時性は変更しない。履歴へ入れることを遅延の理由にしない。
- ドライバーの直後発話が反射への訂正かどうかを、直前反射イベントとの時間・方向・対象軸で判定する。

### B. `disputed()`を最初に判定する

発話処理の順序を固定する。

```text
driver_turn
 → previous_turn / recent_reflex_context
 → dispute_detector
 → disputed() または通常intent
 → authoritative fact lookup
 → response / queue / outcome
```

訂正候補を通常のGAP、fuel、position等へ再分類してはならない。訂正判定が不確実な場合も、元の反射・直前回答を参照した`conversation_dispute_candidate`として保持し、黙って通常質問へ落とさない。

### C. Luna旧値の撤回を必須化する

`open_items`に次を追加する。

- `prior_claim_id`
- `prior_claim_value`
- `luna_value_retracted`
- `replacement_source`

`disputed()`受理時は、単にドライバーの値を保存するだけでなく、`prior_claim_id`を無効化する。撤回完了前の旧値は、回答・要約・戦略計算へ使用禁止とする。

訂正後の最小応答は、次の3要素を含む。

```text
受領 → Lunaの旧値を撤回 → 新しい値を次回から使用
```

例：「わかった、私の0件という記録は撤回するね。3件として次の判断に使うよ。」

### D. 訂正状態の正本を一本化する

`conversation-memory-box.open_items`を訂正状態の正本とする。
`luna-self-memory`は自己反省・傾向の長期要約だけを保持し、未解決・撤回・訂正の状態を二重管理しない。

```text
open_items        = dispute lifecycle authority
luna-self-memory  = resolved lesson / self-reflection summary
```

`luna-self-memory`へ移すのは、`open_items.status=resolved`かつ`luna_value_retracted=true`になった後だけとする。

### E. driver commandとの競合を解消する

同一turnに訂正と命令が含まれる場合の優先順位を固定する。

1. P0安全反射
2. 訂正受領（短いack）
3. 明示されたdriver command
4. 通常の会話回答

訂正と「この周ピット」が同時に含まれる場合は、訂正受領を先に短く発話し、ピット命令を実行状態へ保存する。1つの発話文へ無理に連結しない。
