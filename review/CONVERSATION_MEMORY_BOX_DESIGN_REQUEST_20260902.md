## 1. 現状の「記憶」が何だったか（事実）

実装されているのは記憶モジュール5本
（`session-memory` / `memory-action-layer` / `decision-memory` / `luna-self-memory` / `pddp`）。
中身は**過去セッションの構造化レコード**である。

```
日付・コース・車・ベストラップ・インシデント数・順位・燃費
デブリーフのQA {question, answer}
```

これを毎ターン **3件だけ**引いて渡す（実走ログの `MEMORY_CONTEXT injected=3`）。

そして実際の出力がこれである。

```
前回は「${selected.answer}」と話していた。
```

**ドライバーが前回言ったことを読み上げていた。** 8/31夜には、この経路で
**12時間前の「今回はIncidents 0」を、その日の事実として再放送**した。

**会話の記憶ではなく、発言のコピーを保管していた。**

## 2. さらに重い事実：会話履歴を意図的に捨てている

8/31 実走ログに次の行が **47回**出ている。

```
CONVO [RADIO_HISTORY_EXCLUDED] trigger=...
```

**LLM へ渡す会話履歴から無線を除外している。**

理由は 8/30 Road Atlanta。無線履歴を LLM の会話履歴へ積んだ結果、
**LLM がスポッターコールを捏造した**。その対処が「積むのをやめる」だった。

Telemetry Truth Gate が「正しいライブ回答を遮断して『了解。』へ落としていた」（Build 289 の記録）のと**同じ型**である。
**症状を消すために機能を殺している。** 本件はその2例目にあたる。

## 4. Claude Code の案（叩き台。設計はCodexが確定する）

### 4-1. 設置場所：Electron renderer の localStorage

| 理由 | |
|---|---|
| 配管が要らない | PTT文字起こしを受けるのも Luna の発話を出すのも renderer。**今も全部 `CONVO` としてログには出ているのに、LLM へ渡していないだけ** |
| プライバシー | ドライバーの声が Railway に永久保存されない。9/2 の実名対応と同じ理屈。Yuji が消せる |
| 再起動で消えない | `pw_raceHistory` / `pw_luna_self_memory_v1` と同じ場所 |

毎ターン、この箱をサーバーへ送ってプロンプトへ積む。

### 4-2. 箱の中身（叩き台）

```json
{
  "session_key": "Yuji|<session_id>|Race|Le Mans|Mercedes AMG GT3",
  "turns": [
    { "t": "19:57:32", "who": "luna",   "text": "今回はIncidents 0。…" },
    { "t": "19:58:00", "who": "driver", "text": "インシデント3ついてるんじゃないかな？" },
    { "t": "19:58:05", "who": "luna",   "text": "手元では0って出てた。" }
  ],
  "open_items": [
    { "kind": "訂正", "axis": "incidents", "at": "19:58:00", "acknowledged": false }
  ]
}
```

`open_items` が**訂正16件・正答率0%**を直す場所である。**受理されるまで開いたままにする。**
8/31 に Yuji が14分後・切断を挟んで英語で言い直したのは、これが無かったためである。

### 4-3. ★入れるもの／入れないもの（Road Atlanta 再発防止）

| 箱へ入れる | 入れない |
|---|---|
| 誰が・何を・いつ言ったか | **数字を「事実」として** |
| 訂正された事実と未解決フラグ | 「10周前のGAPは2.0だった」を現在値に使うこと |
| 約束（次周ピット等） | 反射コール（左に車×20回）＝ノイズ |

**数字は毎ターン、その瞬間の事実ブロックから渡す。**
箱の中の数字は「そう言った記録」であって「今の値」ではない、とプロンプトで縛る。

**8/30 の捏造の正しい対処は「履歴を消す」ではなく「履歴の数字に権威を与えない」である。**

### 4-4. 長さの管理

直近30分は生のまま＋それ以前は要約のローリング。
セッション終了時に要約1件を既存の長期記憶（§3の2つ目）へ落とす。

## 5. Codex へ — 設計で決めてほしいこと

1. **設置場所**（renderer localStorage / server / 併用）。当方案は renderer だが、
   ドライバー交代・複数PC（Chief Engineer Mode）を考えると server 側が要る可能性がある
2. **箱の粒度**（セッション単位か、イベント単位か。Practice/Qualify/Race を分けるか）
3. **`open_items` の状態機械**（受理・保留・失効・訂正の訂正）。
   Codex の `disputed()` 契約（`review/CODEX_RESPONSE_TO_VERIFICATION_STANDARD_20260902.md` §3）との統合
4. **反射コールを箱から外す基準**（ノイズと会話の線引き）
5. **要約のタイミングと粒度**（耐久で破綻しない形）
6. **既存5モジュールとの関係**（置き換えるのか、上に載せるのか）

### 6-1. 設計そのものを誰が反証するか

Codex が設計し Claude Code が実装すれば、**作業者と確認者の分離は保たれる**。
しかし**設計自体が誤っていた場合、どちらも止められない**。
Codex は自分の設計を否定せず、Claude Code は実装側である。

**反証は過去ログの再生が担うべき。**
実装したら 8/30〜9/2 の実走ログを通し、**訂正16件が受け止められるか**を見る。
人の意見ではなく、その数字で設計の可否を決める。

### 6-2. 着手前に合格ラインを固定する

> **訂正 0/16 が動かない設計は、他が何点良くても採用しない。**

先に置かないと、また設計論で時間を使う。9/2 は半日それで使った。
