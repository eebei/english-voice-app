---

## 1. 何を作るのか

Luna が**自分の振る舞いについてドライバーから受けた訂正を憶えて、次から変える**仕組み。

### 既存の記憶との違い（重複しないことの確認）

| 層 | 中身 | 実体 | 状態 |
|---|---|---|---|
| 1階a 事実 | コース×車種のベスト・燃費 | `memory-action-layer.js` | 実装済み |
| 1階b クセ | ドライバーの運転傾向 | — | Coming |
| 2階 集合知 | 全ユーザー横断 | — | Coming |
| **新設** | **Luna 自身の振る舞いへの訂正** | — | **本設計** |

既存はすべて「**ドライバーについての事実**」。本設計は「**Luna がどう振る舞うべきか**」で、対象が違う。

## 2. なぜ今の PITWALL にこれが無いのか（実測）

`desktop/renderer.html:2100`

```js
function sendFeedback(btn, val){
  btn.parentElement.innerHTML = val===1 ? '👍 Logged' : '👎 Logged';
}
```

**画面の文字を書き換えているだけで、どこにも保存していない。** サーバー側に受け口も無い。
ドライバーが「今のコールは良くなかった」と押した瞬間に消えている。

記憶が無いのではなく、**記憶する材料を捨てている**。

これが設計の中心。開発中は Yuji が訂正できるが、手を離れたら**ドライバー本人しかいない**。

Claude と Yuji の関係を分解すると：

| 段階 | Claude ↔ Yuji | Luna ↔ ドライバー（設計） |
|---|---|---|
| ① 私が間違える | 長い発話を出す | 不要なタイミングで喋る |
| ② 相手が訂正する | 「24秒は長い」 | 「今はいい」「長い」／👎 |
| ③ **合意を取る** | 会話で「3〜5秒」と決まる | **Luna が一度だけ言い直して確認を取る** |
| ④ 記録する | `feedback` 型メモリ | 訂正レコード |

**③が肝。** ここが無いと、ただの学習になって暴走する。私の記憶が壊れないのは、Yuji が「それは違う」と言える往復があるから。

## 4. 絶対に避けねばならない失敗

### 4-1. LLM に自分の反省を書かせない

Luna に「何が悪かったと思う？」と書かせると、**間違った教訓を書いて永久に適用し続ける**。
本人は正しいことをしているつもりなので、誰も気づかない。1回外しただけで「燃料の話はするな」と学ぶ危険がある。

**教訓は決定論的な観測から作る。** Luna の内省ではなく、起きたことの記録：

```
👎 が押された     → 直前の trigger / intent / 文字数 / 実測秒数 / LapDistPct / Brake / lap
「長い」と言われた → 文字数と秒数は既にログにある
「今じゃない」    → その瞬間がコーナー進入か直線かは取れる
```

私の `feedback` 型記憶も同じ性質で、「Yuji がこう言った」という**事実**であって私の感想ではない。

### 4-2. 一時の感情を恒久ルールにしない

クラッシュ直後の「うるさい！」は、**その状況への反応**であって方針ではない。
1回で確定させない。**同じ型の訂正が閾値回数**（初期案 2回）**溜まって初めて**③の確認へ進む。

### 4-3. 安全を黙らせない

**訂正で抑制してよい対象を閉じたホワイトリストにする。** 既存の「公開APIのextraは値もイベント名も二重ホワイトリスト必須」と同じ思想。

| 調整できる軸 | 例 |
|---|---|
| 頻度 | 同種コールの間隔を空ける |
| 長さ | もっと短く |
| タイミング窓 | コーナー進入では待つ |
| 口調・呼称 | 呼び方、言い回し |

**調整できないもの（ホワイトリスト外＝訂正を受け付けない）**

- P0 安全（`stopped_ahead` / `crash_check` / `incident`）
- Bridge の決定論的事実（燃料・残周回・順位・損傷）
- 契約上の禁止（推測で数値を断定しない 等）

安全項目に訂正が来た場合は、**記録はするが適用しない**。そして理由を一度だけ返す。
「それは安全に関わるから消せない。頻度は下げられる」——**拒否ではなく代案**。

### 4-4. 事実を曲げない

教訓が Bridge の事実と矛盾したら、**必ず事実が勝つ**。
「前回この燃料コールで怒られた」が「燃料が足りない」を黙らせたら本末転倒。
既存の Truth Gate と同じ従属関係に置く。

## 5. 構造

```
① 捕捉   訂正イベントを決定論的文脈つきで記録
             ├ 👍👎（現在は捨てている）
             ├ 走行中の発話（「長い」「今はいい」「その呼び方やめて」）
             └ デブリーフの構造化質問
                        ↓
② 集約   同型が閾値回数 → ルール候補（LLMは使わない）
                        ↓
③ 合意   Luna が一度だけ言い直して確認を取る  ←★ここが Yuji↔Claude の往復に相当
             「コーナー進入では待つようにする。それでいい？」
             ドライバーが否定 → 候補を破棄し、以後同じ提案をしない
                        ↓
④ 保存   ドライバー単位で永続化（合意済みのものだけ）
                        ↓
⑤ 適用   発話前に適用。ただし安全と事実には従属
                        ↓
⑥ 可視化・撤回   何を憶えているか見える／「元に戻して」で消せる
```

### ⑥を必須にする理由

私の記憶は Yuji が全文を読めて、間違っていれば消せる。**見えない記憶は訂正できない。**
ドライバーが「なんか最近喋らなくなった」と感じた時、理由を確認して戻せる導線が無いと、
静かに壊れた製品になる。

## 6. 誤った教訓を自然に殺す仕組み

合意を取っても、後から間違いだと分かることがある。2つ用意する。

1. **反証で弱まる** — 抑制したはずの情報をドライバーが自分から聞いてきたら（例：燃料コールを減らしたのに「あと何周持つ？」と何度も聞く）、そのルールは効いていない。カウントを減らし、閾値を割ったら③へ差し戻す。
2. **時間で薄れる** — 一定期間参照されないルールは失効候補にする。腕前も好みも変わる。

## 7. 実装の置き場所（既存の型に乗る）

注入の仕組みは**既に9本動いている**（`buildProfileNote` / `buildContractNote` / `buildActiveRaceFactsNote` / `buildFuelAuthorityNote` 他）。
`buildEngineerLessonsNote()` は**新しい仕組みではなく10本目**。構造としては同型。

| 段階 | 触る場所 | 規模 |
|---|---|---|
| ① 捕捉 | `renderer.html:2100` `sendFeedback` ＋ 保存先 | 小 |
| ② 集約 | 新モジュール（決定論・UMD・テスト可能） | 中 |
| ③ 合意 | `renderer.html` 発話経路 | 中 |
| ④ 保存 | ローカル or サーバー（下記の判断待ち） | 小〜中 |
| ⑤ 適用 | `buildEngineerLessonsNote()` ＋ 発話ゲート | 中 |
| ⑥ 可視化 | UI 1画面 | 小 |

**①が無いと②〜⑥は作れない。** 材料が貯まらない。

## 8. Yuji に決めてもらう必要があること

1. **保存先** — ローカル（PC買い替えで消える・サーバー費用ゼロ）か、サーバー（引き継げる・2階集合知への道が開く）か。
   後者は個人データを持つことになるので、プライバシーポリシーの範囲確認が要る。
2. **確認を取るタイミング** — 走行中は集中を削ぐ。**デブリーフ時に一度だけ**が有力だが、鮮度は落ちる。
3. **閾値** — 何回同じ訂正が来たらルール化するか（初期案2回）。
4. **2階への接続** — 「多くのドライバーがコーナー進入の発話を嫌った」を全体の初期値にするか。堀になるが、個人の好みを平均で潰す危険もある。

---

## 9. 検証方針（作る前に決めておく）

- 訂正の捕捉・集約・適用は**決定論**なので、実データ形状で単体検証できる。外部API不要。
- **安全ホワイトリストは変異試験必須。** P0 を抑制できてしまう変異を必ず検出すること。
- 合意③が無いままルールが有効化される変異も検出すること。
- 「テストがソース文字列を見ているだけ」にしない（Build 277 / Build 281 で二度踏んだ型）。

## 10. 未確定・私が答えを持っていないもの

- 走行中の「長い」「今はいい」を**STT の揺れを含めて**確実に訂正として拾えるか。八木さんログでは「アンダーがニット」のように崩れる。誤検出でルール化すると悪化する。**実データでの検証が要る。**
- 訂正の**対象特定**。「今のは違う」と言われた時、直前のどの発話を指すか。複数コールが連続した後だと曖昧。
- ドライバーが**キャラクター（Luna / 官兵衛 / 大石）を変えた**時、教訓を引き継ぐか。口調の訂正はキャラ固有、タイミングの訂正は共通と思われるが、切り分けの根拠が無い。
