## 3. 根本原因（2つ・どちらも対症療法では届かない）

### 根本① 記憶が「語る事実」で止まり、「計画」に変換されていない

保存は出来ている（`renderer.html:6452`）:

```js
history.push({ ..., avgFuelPerLap: Number.isFinite(Number(data.avg_fuel_per_lap)) ? ... : null, ... });
```

読み戻しも出来ている（`session-memory.js:161`）:

```js
if (facts.avgFuelPerLap !== null) {
  bits.push(ja ? `平均${facts.avgFuelPerLap.toFixed(2)}L/周` : ...);
}
```

**しかしこれは「前回…平均7.87L/周。」という一文を作るだけである。**
この数字が**ピット周回の計算に入る経路が無い**。記憶は思い出を語るが、計画を立てない。

「あと1周」しか言えないのは、**その場の残燃料からしか計算していない**からである。
記憶の燃費 × グリッドの搭載量 を掛ければ、走り出す前に「7周目」と言える。**その掛け算が存在しない。**

### 根本② 質問の一部だけで intent を決め、残りを捨てている

```
「プランa！何週目？」 → "プランa" に反応 → intent=plan_status → Plan Aの説明文
```

**「何週目？」という問いの本体が、intent 判定の時点で消えている。**
これは Plan A の説明が間違っているのではなく、**聞かれたことに答えていない**という別種の欠陥である。

#### 正確な位置（`engineer-card.js`・判定順）

```js
158:  PIT_DECISION  … 「次のピット.{0,6}(?:タイミング|いつ|何周)」等
                      ★周回を問う語は、すべて "ピット/ボックス" とセットの時だけ一致する
160:  PLAN_STATUS   … 「プラン\s*[ABCＡＢＣ]」で一致   ← 「プランa」がここに掛かった
```

**「何周目？」に単独のパターンが存在しない。** 周回を問う語は "ピット" の修飾としてしか登録されていない。
だから「プランa！何週目？」では "プランa" だけが拾われ、問いの本体は**どのパターンにも当たらないまま消えた**。

（付記：ドライバーは「何**週**目」と発話され STT が 週 で書き起こしている。
既存の正規表現は `(?:ラップ|周|週|州)` と 週 も許容しており、**STT の揺れは既知として対処済み**。
落ちた原因は表記ではなく、**周回を問うパターン自体が独立して存在しないこと**である。）

この2つは独立している。**①だけ直しても、この質問文では②で落ちる。②だけ直しても、①が無いので
「3周走るまで分かりません」としか言えない。両方要る。**

## 4. 設計：グリッドに仮説を持って現れる

現在は **実測を待ってから初めて答える**。3クリーンラップまで何も言えない。
あるべきは **仮説を持って現れ、実測で更新する** である。

```
グリッド（Lap 0・実測ゼロ）
  記憶: Le Mans × AMG GT3 → 7.87 L/周（前回実測・3走分の中央値）
  現況: 搭載 52.3L
  → 「52リッター積んでるね。ここは前回7.9リッター毎周だったから、
      6周は確実、7周目にピットの計画でいこう。3周走ったら実測で見直す。」

Lap 3（実測3周ぶん確定）
  実測: 8.27 L/周（今日は少し重い）
  → 「今日は8.3リッター毎周。計画どおり7周目でいける。」  ← 変化なければ短く

Lap 5（実測が計画を変えた時だけ）
  → 「消費が上がってる。6周目に前倒しだね。」            ← 変わった時だけ喋る
```

**契約:**

| 段階 | 出所 | 言い方 |
|---|---|---|
| グリッド | **記憶**（前回実測） | 「前回は7.9だったから7周目の計画」＝**推定であることを言う** |
| 3周後 | **今日の実測** | 実測へ差し替える。**計画が変わらないなら短く確認だけ** |
| 以降 | 今日の実測 | **計画が変わった時だけ**発話する |
| 記憶なし | — | 「ここは初めてだから、3周走らせて。」＝**捏造しない** |

記憶が無い時に推測で数字を作らないのは既存の規律どおりである。**無いなら無いと言う。**

## 5. 実装の単位（小さい順・各段階で検証可能）

### 段階1 記憶の燃費を「計画」へ通す

`session-memory.js` に `briefingFacts()` があり `avgFuelPerLap` を返している。
これを `fuel-plan-guard.js` の入力へ渡す。現在の入力（`renderer.html:1208`）:

```js
currentFuelL: fuel, avgFuelPerLapL: burn, currentLap: lap,
```

`burn` は**今日の実測のみ**（3クリーンラップ必要）。ここへ**出所つきの推定**を足す:

```js
avgFuelPerLapL: burn,                       // 今日の実測（無ければnull）
fuelPerLapSource: burn ? 'measured_today' : 'memory_previous',
fuelPerLapFallbackL: memoryFacts.avgFuelPerLap,   // 前回実測
fuelPerLapSampleLaps: <前回の周回数>,
```

**`source` を必ず持たせる。** 推定を実測として喋らせないための唯一の防波堤である。

### 段階2 「◯周目」を絶対値で言えるようにする

現在の `pit_decision` は「あと1周」（相対）。絶対周回を持たせる:

```
pit_lap_plan: { lap: 7, basis: 'memory_previous', confidence: 'estimate',
                fuel_start_l: 52.3, burn_l_per_lap: 7.87, sample: 'last_run' }
```

`basis` が `memory_previous` の間は「**前回の実測だと**7周目」と言い、
`measured_today` に変わったら「7周目でいける」と言い切る。

### 段階3 intent が質問の一部を捨てないようにする（根本②）

「プランa！何週目？」を `plan_status` で終わらせない。
**質問に周回・タイミングを問う語（何周目／いつ／この周／次）が含まれていたら、
`plan_status` ではなく `pit_lap_plan` を返す。**

これは局所修正に見えるが、根本は「**intentを1つに決めて残りを捨てる**」構造にある。

**確認済み：両方とも単一intent前提である。**

- `local-intent-router.js:204` の `route()` は `if (regex.test(text)) return answer(...)` の一本道。
  **先に一致した1つを返して終わる。** 今回は `LOCAL_INTENT_BYPASS reason=unhandled` で素通りした。
- `engineer-card.js` も同じ構造で、`158 → 159 → 160` の順に評価し**最初の一致で確定**する。

したがって**複合質問は原理的に落ちる**。パターンを1本足すのは対症療法であり、
「プランaの燃費は？」「次のピットで何位？」など**別の組み合わせが来れば同じことが起きる**。

### 決定（2026-09-04・Yuji 判断）— 並列化する

当方は当初「独立パターンを1本足して済ませる（複合分解は別課題）」を推奨した。
根拠は「実走17件中、複合は1件だから」だった。**この根拠は弱く、撤回する。**

- 17件は**Yuji 1人・1レース**の標本でしかない
- しかも**その1件は失敗している**。起きた複合質問の失敗率は **100%**

Yuji の指摘:

> 尋ね方（質問）はDriverによって変わってくるから、複数を並列に並べて反応させるようにしたほうがいいんじゃないの？

**この指摘が本質を突いている。** 今の構造の欠陥は「複合質問」そのものではなく、

**一部だけ一致したのに、全部を理解したかのように断定して答えること**である。

「プランa！何週目？」は `plan_status` が **confidence 0.96** で掴んで確定させた。
LLM へ流れていれば周回数を答えられた可能性が高い。**部分一致が全文回答になっている。**

### 影響範囲（「大きい」の中身）

| | 判定経路の数 |
|---|---|
| `local-intent-router.js` | **34** |
| `engineer-card.js` | **31** |
| 計 | **65** |

「先に一致した1つで確定」をやめると、**この65本すべてで挙動が変わりうる**。それが影響範囲である。

### リスクを閉じ込める並列化

```
1. 全パターンを評価し、一致したものを全部集める（最初で止めない）
2. 一致が1つ       → 今と完全に同じ経路。挙動は変わらない
3. 一致が2つ以上   → 両方に答える
4. 一致はしたが質問に未回答の部分が残る
                   → 断定せず、決定論的な事実を添えて LLM へ渡す
```

**②が安全装置である。** 既存65本は「1つだけ一致」の時にしか発火しないため、**構造上、退行しない**。
挙動が変わるのは「2つ以上一致する質問」＝**今まさに誤って答えている質問だけ**である。

**④が「尋ね方が変わる」への答え。** 想定外の言い回しは**掴まずに LLM へ渡す**。
決定論的な回答は、形が決まっている質問にだけ使う。

### 並列化で新たに必要になる検証

| # | 検査 | 落とすもの |
|---|---|---|
| 8 | 一致1つの質問65種で、**並列化前後の回答が一文字も変わらない** | 退行 |
| 9 | 「プランa！何週目？」で**2つ一致し、両方に答える** | 部分一致の断定 |
| 10 | 未回答部分が残る質問を**断定しない**（LLMへ渡す） | 想定外の言い回しの誤答 |
| 11 | 変異：並列化を外すと ⑨⑩ が赤くなる | テストが効いていない状態 |

**⑧が最重要。** 65種の回答を並列化前に採取し、後で突き合わせる。**採取を先にやる。**

**選択肢のあるコースで同じ実装を走らせれば、同じ欠陥がもっと大きく出る。**
Le Mans で通ったことを合格の根拠にしない。
