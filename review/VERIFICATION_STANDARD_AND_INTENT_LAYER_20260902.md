## 2. 検証の受入基準（新・両担当に適用）

以後、次を満たさない検証を「検証した」と報告しない。

1. **実行して判定する。** 対象の関数・経路を実際に呼び、返り値で判定する。
   ソース文字列の有無だけの assertion は、契約の固定（採番・配線）以外に使わない。
2. **変異試験を通す。** 修正を1つずつ元へ戻し、テストが赤くなることを確認して件数を報告する。
   生き残った変異は**未テストの穴**であり、塞ぐまで完了としない。
   （実例：8/31 の長さ上限、9/1 の疑問符ガード。どちらも既存assertionを全部通過していた）
3. **実データで再生する。** 手作りfixtureだけで完了としない。保存済み実走ログの該当箇所を通す。
4. **正解を外部から取る。** 自分の計算を自分で採点しない。
   公式リザルト（`eventresult-*.json`）、Bridge権威値、実イベントを正解に使う。
5. **過剰修正を検出する。** 「直った」だけでなく「壊していない」を同じテストで見る
   （相談形を命令にしない／命令形を相談にしない、の両方向）。
6. **未測定を測定済みと書かない。** 測っていない項目は「未測定」と明記する。

## 5. 設計提案 — ローカル vs LLM ではなく、役割の入れ替え

現状の割り当ては、**両方が最も苦手な仕事を担当している**。

```
質問 → 【正規表現】が何を聞かれたか決める → 【LLM】が答えを作る
        理解ゼロ。ここで軸を間違える        数値を捏造しうる
```

提案：

```
質問 → 【LLM】が「何の軸を聞かれたか」だけを分類（数値は一切持たせない）
     → 【ローカル】が事実を計算（identity・時刻・対象・有効性つき／欠ければ事実は存在しない）
     → 【発話層】が人語にする
```

| 層 | 仕事 | 絶対にやらせないこと |
|---|---|---|
| 意図分類 | 質問の軸を決める。相槌・独り言は「質問でない」と判定する | 数値を作る |
| 事実 | 値＋出所＋時刻＋対象＋有効性。1つでも欠けたら**その事実は存在しない** | 文章を作る |
| 発話 | 事実を人語にする。無ければ人語で「無い」と言う | 事実を作る・変える |

期待される効果（**未検証・仮説として記す**）:

- 軸違い（#3,4,5）が構造的に起きない
- 相槌の誤発火（#2）が起きない
- LLM が数値を持たないので捏造しようがない
- 「取得できない」が内部語で出ない（#8）

コスト: 分類は入出力が数十トークンで、現行の「全文脈を渡して答えを作らせる」より**安いはず**。
**これも仮説であり、実測で確かめるまで採用根拠にしない。**
