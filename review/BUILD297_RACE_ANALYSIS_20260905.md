## ② GAPの精度 — 候補と発話の間で値が最大2.0秒動いている

ドライバーの訂正:

```
前は 5.3秒だね。それ。
1秒ずれてるよ。5.5秒 4秒 とか。
```

今朝入れた `GAP_DISPLAY_SYNC` が、その正体を記録していた（**5件すべて rebuild**）:

| 候補生成時 | 実際に発話 | 差 |
|---|---|---|
| 前10.6秒。4秒縮んだ。 | **前11.6秒。** | +1.0 |
| 前5.5秒。1.9秒縮んだ。 | **前7.3秒。** | **+1.8** |
| 前5.1秒。2.2秒縮んだ。 | **前7.1秒。** | **+2.0** |
| 前6秒。2.3秒縮んだ。 | 前5.8秒。 | −0.2 |
| 前4.2秒。1.9秒縮んだ。 | 前4.1秒。 | −0.1 |

**候補を作ってから声が出るまでの短い間に、値が最大2.0秒動いている。**
Le Mans の1周は236秒なので、2.0秒＝**コース長の0.85%＝約115m**。
キューの待ち時間（数百ms）で車が115m動くことはない。**同じ車の値が、2つの異なる出所から出ている可能性が高い。**

- 候補側 … `gap_trend` として作られた文（変化量つき）
- 出口側 … `PitwallGapFreshness.evaluate()` が `lastTelemetry` から読み直した値

**ドライバーの「1秒ずれてる」は、この2つの差を聞いている。**

### 今朝の修正は効いている（別件）

5件すべて `amended_turn=true`。**表示・音声・会話Boxは揃った。**
ドライバーも「さっきの**前11.6秒**っていうのは」と、**発話された方の値**で聞き返している。
つまり**表示と音声のズレは解消した**。残っているのは**値そのものの精度**である。

### 変化量が捨てられる問題も実データで出た

`前10.6秒。4秒縮んだ。` → `前11.6秒。`
値は **増えている**のに元の文は「4秒縮んだ」と言っていた。**捨てて正解だった**が、
ドライバーは接近／離脱の情報を失っている。既知の未修正項目。
