## 2. ★4走行連続の「レース結果が届かない」原因が確定した

依頼書には無い項目だが、**今回の最大の収穫**なので先に出す。

Build 293 で投入した `RACE SUMMARY GATE` が 35 サンプル出力し、**`may=True` は 0 回**。

```
14:50:48 may=False should_fire=True lap_time_settled=True
         latest_lap_recorded=False(rec_lap=12 cur_lap=13 rec_time=236.772)
```

完走の瞬間、`should_fire` と `lap_time_settled` は成立している。**`latest_lap_recorded` だけが開かない。**

```python
_latest_lap_recorded = bool(
    session_laps and session_laps[-1].get('lap') == lap
    and session_laps[-1].get('time') == round(lapTime, 3))
```

`session_laps[-1]['lap']` は**完了した**周（12）、`lap` は**走行中の**周（13）。
**13周目はレース終了により永遠に完了しない**ので、完走時点でこの条件は開かない。

`RACE RESULT` / `Session summary dispatched` / `Session summary pending` すべて **0件**。
8/30・8/31朝・8/31夜・9/2 の**4走行すべてで同じ**。
最終順位・iRating・公式incidents がデブリーフへ届かない直接の原因である。

## 3. 再生 fixture が、当方の誤った根本原因を暴いた

**この節は自分の失敗の記録として残す。**

最初の fixture では **summary が発行されてしまい**、上記の仮説が成立しなかった。
原因は fixture の誤りで、**13周目を「完了した通常周」として `session_laps` に入れていた**（`rec_lap=13`）。
実走では13周目は走行中に終わっており `rec_lap=12` である。

13周目を通常走行ループから外したところ、実走と完全に一致した（`may=True` 0件、summary 0件）。

**この修正が無ければ、誤った根本原因を報告していた。**
`poll_iracing()` を実際に回したから出た誤りであり、静的検査でも純関数テストでも絶対に出ない。
9/2 朝のクラッシュ（`_gate_state` 衝突）と同じ型で、**「実行して判定する」以外に検出手段が無い。**

## 5. 限界（依頼書 §4 への回答）

**GAPの正解値は、このログからは再計算できない。**

デバッグログに残るのは Bridge が**採用した**値であって、iRacing 側の真値ではない。
したがって `direction_conflict_rank_vs_physical` 301件について、
「破棄が正しかった」のか「破棄すべきでなかった」のかは**このログだけでは判定できない**。

**方式比較では、GAP の正確性を絶対値で採点できない。** 採点できるのは内部整合だけである。

- 同一クラス・同一対象車・同一取得時刻が1レコードに固定されているか
- 同じ質問に同じ入力で同じ答えを返すか（反復整合）
- 時系列で符号や対象が反転しないか

**絶対的な正確性は、iRacing公式リザルト（`eventresult-*.json`）か、
画面値と同時刻で突き合わせた実走でしか採点できない。** 今回はどちらも無い。

もう1点。**残り周回マイルストーンの赤は、まだ実装の欠陥と断定できない。**
再生では 5/3/2/1 いずれも未発話だったが、実走では 5 と 3 は発話している。
**fixture の周回進行が実走より粗い**可能性があり、fixture 精度を上げてから判定する。
現時点でこれを「実装の欠陥」として直しにいくのは早い。

## 6. ★Claude Code の意見 — 「6方式の比較」という枠組みに反対する

依頼書 §2 は6つを**同一fixtureで比較**するよう求めている。**この枠組みは正しくないと考える。**

**6つのうち、本当に択一なのは1つだけである。** 残り5つは互いに独立した修正であり、
比較して1つを選ぶ性質のものではない。比較の形にすると、
**「全部やるべきもの」を「どれか選ぶもの」に変えてしまい、時間を失う。**

| # | 方式 | 当方の判定 | 理由 |
|---|---|---|---|
| 1 | 順位／物理距離衝突時 fail-closed（現行） | **択一の対象** | ↓ |
| 2 | クラス固定＋物理距離優先 | **択一の対象** | ↓ |
| 3 | 直近2〜3ポーリング一致時のみ発話 | **1・2と直交。併用可** | 平滑化はどちらの方式にも乗る |
| 4 | FINISHED/CHECKERED で燃料・ピットキュー取消 | **無条件で実装すべき** | 択一の余地が無い |
| 5 | 残り周回 5→3→2→1→Final の強制 | **保留。方式の前に原因究明** | §5の通り fixture 精度が未確定 |
| 6 | Plan質問に周・給油量・根拠を一体で返す | **無条件で実装すべき** | 択一の余地が無い |

### 6-1. 本当の択一は #1 vs #2 だけ。そして当方は**どちらでもない**と考える

**現行の fail-closed（#1）は、自動発話としては正しい。** 推測の GAP を勝手に喋る方が害が大きい。
**しかし質問への回答としては誤っている。** 8/31 の実走で同じ型が出ている。

> `19:35:44` ドライバーの相槌 → `leader_gap` →「クラス首位とのGAPは取得できない。直前車のGAPでは代用しない。」

**沈黙も規約文も、ドライバーには「答えなかった」としか映らない。**

`#2` のクラス固定＋物理距離優先も、Le Mans では危うい。
**全49台・IMSA23 34台**の混走で、クラスをまたいだ物理距離は意味を持たない。
クラス固定は**必要条件だが十分条件ではない**。

当方の案は**第3の道**である。

> **自動発話は fail-closed のまま（#1を維持）。質問への回答だけ、`unavailable` に理由と次の行動を必ず付ける。**
>
> 現状: `クラス首位とのGAPは取得できない。直前車のGAPでは代用しない。`
> 提案: `クラス首位のGAPは対象車が確定してない。次の計測で出す。` ＋ **実際に次で出す**

これは Codex 自身の `unavailable({axis, reason, next_action})` 契約そのものであり、
**新しい方式ではなく、既に合意した契約を GAP へ適用するだけ**である。
`direction_conflict` 301件は「破棄」ではなく「**保留して次で答える**」に変わる。

### 6-2. #3（時系列平滑化）は条件付きで賛成。ただし適用範囲を限定すべき

2〜3ポーリング一致を待つのは、**GAPのような連続値には妥当**。
しかし**安全コール（左右の車・停止車両・黄旗）に適用してはならない。**
遅延が事故に直結する。

**適用範囲を「質問への数値回答」に限定するなら賛成。自動の安全コールには反対。**

### 6-3. #5（マイルストーン強制）に反対する

「強制」は危険である。**データが誤っていても喋る**ことになる。

実走で 5 と 3 が出て 2 と 1 が出ていない。これは**機能の欠落ではなく、
条件・dedupe・しきい値のどれかの不具合**である可能性が高い。
**原因を特定せずに「強制的に出す」を足すと、誤った周回数を確実に喋る実装になる。**

先にやるべきは、fixture の周回精度を上げて **2周・1周が出ない理由を特定すること**。
その上で「単一の権威から導出し、冪等に発話する」設計にする。強制ではない。

## 7. 着手順の提案（当方の意見）

1. **`latest_lap_recorded` の修正**（§2）
   4走行分の証拠があり、原因が特定済み。**これが通らない限り下流が全部止まる** —
   最終順位が無ければデブリーフの事実が無く、PDDP も incidents 検証も動かない。
   再生テストが既に赤で、直れば緑になる。**最も安く、最も効く。**
2. **#4 CHECKERED後のキュー取消**（再生で赤・原因明白・副作用なし）
3. **#6 Plan質問の一体回答**（8/31から同じ失敗が続いている）
4. **#1/#2 の代わりに 6-1 の第3案**（`unavailable` に理由と次の行動）
5. **#3 を質問回答に限定して適用**
6. **#5 は原因究明が先**。fixture 精度を上げてから

**1〜3は択一ではないので、比較に時間を使わず実装すべき**というのが当方の意見である。
