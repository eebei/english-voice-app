## 1. 【P0】LLM がスポッターコールを捏造している

**最も重い問題。安全コールの信頼が根本から崩れる。**

### 実測証拠

```
[16:21:08] USER   ちょっと強引すぎちゃった。
[16:21:10] INTENT_ROUTE intent=conversation authority=llm
[16:21:10] LunaJP 次のラップは白紙。リセットしよ。左に車。
           → TTS chunk chars=9（次のラップは白紙。）
           → TTS chunk chars=7（リセットしよ。）
           → TTS chunk chars=4（左に車。）      ← kind=reply_chunk / prio=2
```

この時刻に `DIRECTOR pass: side_by_side` は**存在しない**。つまり「左に車。」は `CarLeftRight`（iRacing公式スポッター値）由来ではなく、**LLM が会話の続きとして書いた文字列**であり、P0 安全コールではなく P2 の雑談チャンクとして再生された。

同型がもう1件：
```
[16:23:13] USER   むしろ クラッシュしてるね。
[16:23:15] LunaJP わかった。ピット前に確認する。今はドライビングに集中して。左に車。
```

そしてドライバーは、この捏造コールに対して2度も反論している：
```
[16:21:25] USER 左は ウォールしかないです。
[16:23:41] USER 左全然 車いないです。
```

**ドライバーは実在しない車を警告され、それを否定するために2回もPTTを押した。** 走行中の集中を削るだけでなく、以後の本物の安全コールの信用も失う。

### 根本原因（コード）

`desktop/renderer.html` の `injectRadio()` は、**全ての無線コールを LLM の会話履歴へ assistant 発言として書き込んでいる**。

```js
addMsg('ai',text);
pushMsg({role:'assistant',content:text});   // ← 無線が会話履歴に入る
```

結果、LLM は「自分が直前に『左に車。』と言った」文脈を持ち、次の返答で同じ語調を自然に継続する。同じ機構で `TELEMETRY_TRUTH_GATE` が捕まえた4件も説明できる：

```
blocked LLM vehicle-state claim: 了解。P10、0.9秒前。
blocked LLM vehicle-state claim: 了解。右側、注意。P9。ナイスパス。
blocked LLM vehicle-state claim: 了解。このまま行こう。前0.9秒。詰まってきてる。
blocked LLM vehicle-state claim: データ来てる。残り3分。
```

Truth Gate は**数値を伴う自車状態の主張**は止めたが、**スポッター語彙（左に車／右側注意）は素通り**した。捕まえたのが4件、素通りが少なくとも2件。

### さらに素通りしたもの：ライバルに関する捏造

```
[16:35:02] USER   iも苦労してるね。
[16:35:03] LunaJP そうね。前、セクター2で落としてる。ペース、まだ詰められる。
```

**他車のセクタータイムは取得していない。** `competitor_status` が持つのは `last_lap_s`（完了ラップ1本）だけで、ライバルのセクター情報はどこにも存在しない。これは Truth Gate の対象外（自車状態ではない）を通り抜けた完全な作り話。

### 改善方向

1. **無線コールを LLM 会話履歴へ入れない。** 無線は「Lunaの発言」ではなく「別系統の出力」として扱い、履歴には `[radio]` の要約メタだけを、または一切入れない。LLM が知る必要があるのは *事実*（現在GAP・順位）であって *自分が喋った文面* ではない。
2. **出力フィルタでスポッター語彙を禁止する。** LLM の返答に「左に車／右に車／◯側注意／後ろから来てる／スピン／黄旗」等の安全コール語彙が現れたら、その文だけ落とす（返答全体は殺さない）。安全コールは決定論経路の専権とする。
3. **Truth Gate をライバル主張へ拡張する。** 「他車のセクター／他車の走り方／他車のタイヤ」は、対応する実測ソースが無い限りブロックする。現在は自車の数値主張しか見ていない。

## 2. 【P0】マルチクラス接近コールが毎周ループする（29回）

### 実測証拠

```
16:08:24 GTP2台、固まって5.6秒後方。     16:34:20 GTP、5.8秒後方。
16:09:10 GTP2台、固まって2.8秒後方。     16:34:41 GTP、5.7秒後方。
16:11:54 GTP、3.8秒後方。                16:35:04 GTP、2.9秒後方。
16:11:57 GTP、2.9秒後方。                16:36:13 GTP、1.1秒後方。
16:18:06 GTP、5.8秒後方。                16:37:26 GTP、5.9秒後方。
16:18:32 GTP、2.9秒後方。                16:37:51 GTP、2.9秒後方。
16:24:43 GTP、5.7秒後方。                16:39:10 GTP、5.6秒後方。
16:25:09 GTP、2.9秒後方。                16:39:36 GTP、3秒後方。
16:26:18 GTP、6秒後方。                  16:39:53 GTP、2.9秒後方。
16:26:53 GTP、2.6秒後方。                16:41:50 GTP、5.5秒後方。
16:31:11 GTP1台が5.8秒後方、その後に1台。 16:42:15 GTP、2.8秒後方。
16:31:37 GTP1台が2.8秒後方、その後に1台。 16:42:45 GTP2台、固まって5.7秒後方。
                                          16:43:07 GTP2台、固まって3秒後方。
                                          16:45:00 GTP、5.7秒後方。
                                          16:45:25 GTP、3秒後方。
                                          16:46:47 GTP、5.8秒後方。
                                          16:47:15 GTP、3秒後方。
```

**値の分布：`2.9秒` が6回、`5.7〜5.8秒` が6回、`3.0秒` が3回。** 実質「5.7秒」と「2.9秒」の2値がレース中ずっと反復されている。

### 根本原因（コード）

`irsdk-bridge/bridge.py` の段階ラダー：`MC_PREPARE_SEC=6.0`（準備）→ `MC_IMMINENT_SEC=3.0`（直前）→ `MC_REARM_SEC=8.0`（再武装）。

問題は **`multiclass_stage` のキーが「クラス名（GTP）」であり、車ではない**こと。

```python
for _cn in list(multiclass_stage.keys()):
    _g2 = _mc_observed_groups.get(_cn)
    if _g2 is None or min(_g2) > MC_REARM_SEC:
        multiclass_stage.pop(_cn, None)     # 再武装
```

GTP が9台いる31台のフィールドでは、1台が抜き去った直後に**次のGTPが8秒以遠に現れる**。すると `min(_g2) > 8.0` が成立して再武装し、また6秒→3秒のラダーを最初から登る。**「GTPに抜かれる」というイベントが毎周発生する以上、このループは構造的に止まらない。**

さらに、コールに **車番もクラス内の識別子も無い**ため、ドライバーには「さっきの車がまた近づいたのか、別の車なのか」が判別できない。

### ドライバーは実際に数字を否定している

```
[16:18:32] LunaJP GTP、2.9秒後方。
[16:18:40] USER   まだ3秒以内にも入ってない。
[16:18:42] LunaJP その数値は確認できない。質問をもう一度短く教えて。
```

**8秒後にドライバーが「3秒以内に入っていない」と明確に訂正したのに、受け皿が無い。** Phase F2 で GAP には「訂正されたソースを保留し、再観測まで未確認と言う」導線を作ったが、**マルチクラス接近コールには同じ導線が無い**。結果、否定された直後も同じ計算で喋り続けた。

なお `_mcgap = -_pd * player_last_lap` は「自車のラップタイム換算での距離」であり、ドライバーが画面で見ている iRacing の相対時間とは定義が異なる。どちらが正しいかではなく、**ドライバーの見ている数字と一致しない数字を、根拠を添えずに言い続けたこと**が信頼を壊した。

### 改善方向

1. **キーを車（CarIdx）にする。** 同じ車には1スティントに1回。別の車なら別のイベントとして扱い、車番を添える（「GTP #7、3秒後方」）。
2. **クラス単位の発話予算を設ける。** 「上位クラス接近」は1周につき最大1回、レース全体で N 回まで。予算を超えたら、本当に危険な最終段（1秒以内・並走）だけに絞る。
3. **数字ではなく行動を言う。** 「GTP、2.9秒後方」は行動を含まない。「GTP、次の左コーナーで来る。イン開けて」まで言えて初めて価値が出る。距離だけしか言えないなら**言わない方が良い**。
4. **ドライバー訂正の受け皿を横展開する。** Phase F2 の保留機構（訂正→ソース保留→再観測まで未確認）を、GAP だけでなくマルチクラス接近にも適用する。「まだ3秒以内に入ってない」で該当車の段階をリセットし、次の実測まで黙る。

## 3. 【P1】サイドコールの機械的連呼（33回）

### 実測証拠：ピットアウト直後の39秒に8連発

```
16:28:17 左に車。   16:28:32 右に車。   16:28:44 右に車。   16:28:56 右に車。
16:28:23 左に車。   16:28:38 右に車。   16:28:50 右に車。
16:28:29 左に車。
```

`SIDE_BY_SIDE_COOLDOWN_S` による side ごとのクールダウン（約6秒）で dedup しているが、**6秒ごとに機械的に鳴る**ことと同義になっている。ピット退出直後は必然的に多数の車に抜かれる局面であり、そこで6秒おきに「右に車」と言われても行動は変わらない。

`CarLeftRight` 自体は iRacing 公式値なので**個々のコールは嘘ではない**（§1のLLM捏造とは別物）。問題は密度と情報量。

### 改善方向

1. **局面認識で束ねる。** ピットアウト〜ブレンド完了、スタート直後、フルコースコーション明けは「多数に抜かれる局面」と分かっている。個別コールをやめ、局面の頭で1回「後ろからGTPが数台来る。ラインキープ」と言って以後は黙る。
2. **同一相手の連続コールを1回にまとめる。** `CarLeftRight` は car_idx を持たないが、`competitors` の物理位置から並走中の相手を推定して同一性を持たせられる。
3. **「両側」「クリアになった」を言う。** 一番欲しいのは「もう抜けた、行っていい」で、今はそれが無い。

## 4. 【P1】ドライバーの訂正・質問が届かない

| 時刻 | ドライバー | Luna | 問題 |
|---|---|---|---|
| 16:11:18 | ルナ 継続して gdpのコード教えて。 | ごめん、わたしはレースエンジニア。 | STTが **GTP→gdp**、**ギャップ→コード** に化けた。プログラミングの依頼と誤解して拒否 |
| 16:18:40 | まだ3秒以内にも入ってない。 | その数値は確認できない。質問をもう一度短く教えて。 | 接近コールへの**訂正**なのに、訂正として扱われない |

`desktop/local-intent-router.js` は首位GAPの判定に `/総合|GTP|gdp|overall/i` を持っており、**`gdp` という表記揺れは既に既知**。にもかかわらず「gdp 来てる？」「gdpのコード教えて」は intent に届かなかった。

### 改善方向

1. **STT正規化を入口で一度だけ行う。** `gdp`／`GDP`／`ジーティーピー` → `GTP`、`コード`（GAP文脈）→`ギャップ` を、分類・router・LLM の**手前**で正規化する。各所の正規表現に `gdp` を足して回るのは破綻する。
2. **マルチクラス接近コールにも訂正導線を作る**（§2-4と同じ）。
3. **「その数値は確認できない」を最終手段にする。** これは Truth Gate が正答を落とした時の文言で、8/30 RB Ring でも同じ形が出た。今回2回出ている。**確定値を持っている質問（インシデント数・クラス別GAP・GTP接近状況）は local intent で即答できるようにする。**


**「給油量、一緒に決めよ」と言ったまま、給油量の話は最後まで一度も出ない。** ドライバーは何リットル入れたのかを知らないままレースを続けた。Tunnel Completion Rule（入口があるなら出口を必ず作る）の違反であり、しかも自分から言い出した約束を落としている。

## 8. 改善の設計原則（優先順）

### 原則1：安全コールの発生源を1つにする

**LLM は安全コールを一切書けない。** 無線を会話履歴へ入れることをやめ、出力側でもスポッター語彙を落とす。Truth Gate をライバル主張へ拡張する。
→ §1。**最優先。信頼の土台であり、他の全ての改善はこれが前提。**

### 原則2：発話に予算を持たせる

現在は各コールが独立に「鳴ってよいか」を判断しており、**全体で何回喋ったかを誰も見ていない**。カテゴリ別の予算（例：traffic 系は1周1回・レース合計15回）を導入し、予算内で最も価値の高いものを選ぶ。予算を使い切ったら、P0安全直結だけが通る。
→ §2、§3。110回→30回以下が目標。

### 原則3：数字ではなく行動を返す

「GTP、2.9秒後方」「左に車」「P12」は、どれも**ドライバーが次に何をすべきかを含まない**。同じ情報量なら「GTP、次の左コーナーで来る。イン開けて」「クリア、行っていい」の方が短くて役に立つ。**行動に翻訳できない情報は、言わない方が良い。**

### 原則4：ドライバーの訂正は必ず着地させる

「まだ3秒以内に入ってない」「左は壁しかない」は、**システムが間違っている証拠をドライバーが無償で提供してくれている瞬間**。Phase F2 で GAP に作った保留機構（訂正→ソース保留→再観測まで未確認）を、マルチクラス接近・サイドコールにも横展開する。

### 原則5：自分の約束を台帳に載せる

「一緒に決めよ」と言ったら決めるまで終わらない。会話上の約束にも fate trace を付ける。

## 9. 着手順の提案

| 順 | 項目 | 根拠 | 規模 |
|---|---|---|---|
| 1 | 無線を LLM 履歴へ入れない＋出力側スポッター語彙フィルタ | §1 P0・信頼の土台 | 小〜中 |
| 2 | Truth Gate をライバル主張へ拡張 | §1・捏造の残り穴 | 小 |
| 3 | マルチクラス接近を CarIdx キー化＋周回予算＋車番付与 | §2 P0・29回の元 | 中 |
| 4 | STT正規化（gdp→GTP等）を入口で一度だけ | §4・同一レースで3回失敗 | 小 |
| 5 | サイドコールの局面束ね（ピットアウト・スタート） | §3・33回の元 | 中 |
| 6 | 訂正受け皿の横展開（F2機構の再利用） | §2、§4 | 中 |
| 7 | 約束の follow-up 台帳 | §5 | 中 |
| 8 | 順位コールのブレンド中抑制・crash_check の一問化 | §6 | 小 |

1・2・4・8 は小さく、**次の実走までに入れれば体感は明確に変わる**。3・5 が本丸で、110回の過剰発話の過半を占める2種類を直接叩く。
