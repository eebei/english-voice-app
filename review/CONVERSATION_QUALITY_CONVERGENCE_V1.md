## 3. 3層モデル — 壊れている場所は1つではない

Yujiの言葉：「しっかりした数字はLunaの手前まできてるだろ？ P12-P15の間にブレンドなど」
これはほぼ正しい。ただし正確には3層あり、層ごとに壊れ方が違う。

### 第1層：生の実測 — 項目別に判定する（一括で「健全」としない）

**注意：本節の初版は第1層を一括で「健全」と書いていた。これは誤り。**
8/31ログで誤りが検出されなかったのは GAP・燃料・順位・ラップ・ピット時間であり、
**同じログで Incidents は捏造されている**（`prev_incidents or 0`）。
第1層は項目ごとに正本・欠損時挙動・実測での一致を個別に判定すること。§9-2 が受入条件。

8/31 11:34:47（Yujiが「この10ピット入ったら？ ブレンドする時どうかな？」と聞いた瞬間）に
Bridgeが保持していた値：

```
Lap:12  Pos:5  Fuel:19.8L  gapAhead:0.5  gapBehind:0.1  LastLap:91.25
実測燃費 2.70L/周（11:23:16 成立）  Plan A  GT3単一クラス23台
```

実際の結果も記録されている：

```
PIT EVENT FACT: {"entry_lap":12,"exit_lap":13,"lane_total_s":30.5} P5 → P7
```

**答えるための材料は全て揃っていた。** これらの項目に誤りは検出されていない。
ただし同じセッションの Incidents は不明を0と断定しており、**第1層は一様ではない**。

### 第2層：導出される予測 — 外れており、しかも幅を潰している

同ログ 11:35:53：

```
PIT EXIT SHADOW actual: {"actual_class_position":7,"likely_position":12,
  "likely_error_positions":-5,"inside_best_worst":false,"model_version":4}
```

予測P12に対し実測P7、**5ポジションの誤差、かつ自身のbest/worst範囲の外**。
さらに発話は `範囲P12〜P12` ＝ **幅ゼロで断言**していた。

Yujiが求めた「P12〜P15の間」は、単なる言い回しの話ではなく
**外れうる予測を正直な幅で述べる**という第2層の要求である。
第3層だけを直しても解決しない。

### 第3層：人語への翻訳 — 存在しない

第1層の正しい数字も、第2層の怪しい数字も、同じ内部語のまま口から出る。
`fail-closed` と `authority` は設計通り動作しており、
**その正しさがそのまま会話を壊している**という逆説が現状。

### 同じ瞬間を、同じ材料だけで書き直すと

> 今のP5から入ると、戻りはだいたいP12からP15の間。
> 前が0.5秒、後ろが0.1秒だから、今は挟まれてる。次の周のセクター3で判断しよう。

新規データは1件も要らない。違いは「幅を潰さないこと」と「規約でなく状況を喋ること」。

## 4. 収束の定義と見積もり

### 収束するのは型であり、実例ではない

- **装置の初期コーパスに必要な新規走行：0回。** 既存ログが手元に21本ある。
  8/31の1本から9型のうち7型が抽出できた。Yujiが走らなくても着手できる。
- **新しい型が出尽くすまで：実走3〜5本。** ただし**条件を意図的に散らした場合**に限る。
  同一条件のスプリントを10本走っても同じ型しか出ず、情報量はほぼゼロ。
- **「同じ指摘を二度しない」状態まで：合計7〜9本。**

### 散らすべき条件（優先順）

1. **黄旗／コーションが出るレース** — `HANDOFF.md` で未検証と明記。⑦⑨が出やすい。手元の実走ログ2本とも `yellow_flag=0`
2. **マルチクラス** — Road Atlantaで⑥が最悪化した条件
3. **耐久／ドライバー交代** — Chief Mode・Team Plan経路が実走未通過
4. **Yuji以外のドライバー**（八木・まーぼー等）— ③④の新実例源

### 収束判定（Yujiが担当者を測る物差し）

> **連続する2本の実走ログで、①新しい型が0件、かつ②既に修正済みの型の再発が0件。**

これを満たすまで、担当者の「良くなりました」を合格として扱わない。
装置がこの2値を毎回自動出力すること。

### 見積もりの前提と限界（正直に）

- 根拠は8/31の1本＋Road Atlanta分析。**サンプルが少なく、伸びる可能性がある。**
  最初の2本で新型が何件出たかで、この見積もり自体を更新して報告する。
- 装置では**絶対に判定できない領域**が残る：自然さ、間合いの快適さ、信用できる相棒に聞こえるか。
  装置が潰すのは「**明確に間違っている発話**」であり、「**つまらない発話**」は残る。
- 担当者が自分の直したものだけに合格を出す装置を書ける危険がある。
  **型の定義と判定はCodexが独立に反証すること。** ログはYujiが外から持ち込む入力なので汚せない。

## 5. 作業の順序

| | 内容 | 性質 |
|---|---|---|
| **A** | 評価装置（既存ログをリプレイし、型で合否を出す） | 土台。これ無しに改善が次ビルドへ保存されない |

## 6. 計装の欠落 — 「正しい沈黙」を欠陥と数えない

8/31 11:34:48 の回答は再生開始まで6.3秒（`queue_ms:6276`）かかった。
Claude Codeは当初これを欠陥として報告したが、**誤りだったので訂正する。**

これは設計通りの発話タイミングゲートである：

- `desktop/renderer.html:2977` `speakWindowOk` = **舵角 約7度未満 かつ Brake 12%未満**
- `desktop/renderer.html:3160` 窓が閉じている間、`immediate` でない発話はキューに保持
  （コメント：「コーナー／ブレーキング中は、P0/P1安全無線と期限付きピット手順だけ開始できる」）
- `reply` / `reply_chunk` は `immediate:false` ＝ 待たされる側

当時 gapAhead 0.5 / gapBehind 0.1 で挟まれており、ブレーキと舵を使い続けていた。
**設計通りに黙っていた。**

2つ目の 12.5秒（`queue_ms:12481`）は別要因で、
1つ目の再生終了が 11:34:58、2つ目のTTS開始が 11:35:00 ＝ **直列化待ちが大半**。

### ここから出る要件

`CONVO [SPEECH_LATENCY]` は保留理由を記録していない（`"reason":null`）。
そのため**「窓が閉じていて正しく待った」と「単に遅い」がログから区別できない**。
Claude Codeが誤読した原因もこれである。

> **A（評価装置）の前に、保留理由を `SPEECH_LATENCY` へ記録する。**
> これが無いと、装置は「正しい沈黙」を欠陥として数える。

未決（Yuji判断）：回答が2チャンクに分割され、窓が開いた時に細切れで届く挙動を変えるべきか。
実走での体感で決めるべき事項であり、担当者が判断しない。

5. **装置の設計。** 型判定を機械で行う具体案。誤判定（正しい沈黙・正しいfail-closed）を

## 9. Codex追加必須項目（Yuji指示・2026-08-31）

以下の4点は**必須**であり、Codexのブラッシュアップに含めること。
§7の依頼6項目より優先する。1〜4のいずれかが満たされない案は差し戻す。

### 9-1. P0捏造・過去発話echoを範囲外にせず、会話品質の中核として扱う

初版は「本MDの範囲外・別作業」と書いていた。**撤回する。**

- `bridge.py:2986` / `:3332` の `'incidents': prev_incidents or 0`（型①捏造）
- `renderer.html:5209` の `` `前回は「${selected.answer}」と話していた。` ``（型⑤echo）

この2件は「たまたま見つかったバグ」ではなく、**Lunaが嘘をつく／人の言葉を無断で読み上げる**という、
会話が成立しない理由そのものである。装置の設計・KPI・収束判定のすべてがこの2件を対象に含むこと。
装置がこの2件を検出できないなら、その装置は不合格。

### 9-2. 第1層は「健全」と一括せず、項目別に健全性判定する

§3の初版の誤りを正す。**項目ごとに次の表を埋めること。**空欄が1つでもあれば「健全」と書かない。

| 項目 | 正本（どこが決めるか） | 欠損時の挙動 | 実測での一致確認 | 判定 |
|---|---|---|---|---|
| GAP（前／後） | | | | |
| 燃料（残量・消費率） | | | | |
| 順位（クラス／総合） | | | | |
| Incidents | Bridge `PlayerCarMyIncidentCount` | **`or 0` で0に化ける＝不合格** | 8/31実走で本人申告4〜5に対し0 | **不合格** |
| ラップタイム（best／last） | | | | |
| ピット実測（lane／stall／entry-exit lap） | | | | |
| リーダー情報（lap／GAP） | | | | |
| セッション残（周回／時間） | | | | |

「欠損時の挙動」欄で、**不明を0・空文字・既定値へ丸めている箇所は全て型①の予備軍**として扱う。
`or 0` `|| 0` `?? 0` の類を全経路で洗い出すこと。

### 9-3. 「7〜9本」は仮説値とし、評価装置の実測後に再計算する

§4の見積もりは**サンプル2本からの仮説であり、確定値として扱わない。**

- 装置が過去ログを型でラベル付けした時点で、**新型発見率の実測曲線**を作り、そこから再計算する。
- 再計算までは、チャット報告・HANDOFF・本MDのいずれでも「あと◯本で終わる」と断定しない。
- 実走2本ごとに見積もりを更新し、**前回値との差分を明示して報告**する。

### 9-4. KPI化する（6指標）

会話品質を主観でなく数値で追う。装置はレース1本ごとに以下を出力すること。
分母・分子・正本が曖昧な定義は差し戻す。

| KPI | 定義（分子／分母） | 正本 | 関連する型 |
|---|---|---|---|
| **質問軸一致率** | ドライバーの質問の軸と回答の軸が一致した数 ÷ PTT質問数 | ログの `CONVO [USER]` と直後の応答 | ③④ |
| **数値誤答率** | 実測正本と不一致、または不明を断定した数値発話数 ÷ 数値を含む発話数 | Bridge権威・実結果（`PIT EVENT FACT` 等） | ①② |
| **echo率** | ドライバーの自由文をそのまま含む発話数 ÷ 総発話数 | `CONVO [USER]` との文字列一致 | ⑤ |
| **訂正反映率** | 次の該当場面で反映された訂正数 ÷ ドライバーの訂正・抗議数 | 訂正発話と後続の同型場面 | ⑨・記憶 |
| **不要発話率** | 連呼・重複・局面束ね後に不要と判定される発話数 ÷ 総発話数 | 型⑥⑦⑧の判定 | ⑥⑦⑧ |
| **戦略回収率** | 回収された宣言数 ÷ 宣言した行動数（「次周ピット」等） | 宣言発話と実イベント | ⑨ |

**8/31ログでの初期値を必ず算出し、以後の基準線とすること。**
基準線が無ければ改善したかどうかを誰も検証できない。

### 9-5. 受入条件（報告の禁止事項）

> **連続する2本の実走ログで、①新しい型が0件、かつ ②既知の型の再発が0件。
> これを満たすまで「収束完了」と報告しない。**

加えて、次を満たすまで完了扱いにしない。

- 9-4の6 KPIが**レース1本ごとに自動出力**されている
- 9-2の項目別表が**全項目埋まっている**
- 9-1の2件が**装置で検出できることを実証**している（修正しただけでは足りない）

個別修正の完了報告は「型◯の実例を1件潰した」までしか主張してよい。
「会話が改善した」「安定した」「問題ない」は、上記受入条件を満たすまで書かない。
これは Claude Code / Codex 双方に適用する。
