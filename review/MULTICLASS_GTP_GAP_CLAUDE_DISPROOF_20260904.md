## 反証① 混入は構造的に起こり得ない

`bridge.py:5735-5765` の候補ループ:

```python
_mcls = car_class_map.get(_mi, -1)
if _mcls == -1 or _mcls == player_class_id or _mrel <= player_rel_speed:
    continue                      # ← 同クラス(GT3)はここで全部落ちる
...
_cn = _norm_class_name(car_class_name_map.get(_mi)) or 'faster class'
_mc_groups.setdefault(_cn, []).append(_mcgap)   # ← 名前もGAPも同じ _mi
```

**自車と同じクラスの車は、候補集合に入る前に除外される。** GT3のGAPが `_mc_groups['GTP']` へ入る経路が無い。
クラス名とGAPは同一ループ変数 `_mi` から取っており、既に車両単位で原子的である。

供給元も同じレコードである（`bridge.py:2884-2890`）:

```python
for d in info.get('drivers', []):
    car_class_map[d['car_idx']]      = d['class_id']
    car_class_name_map[d['car_idx']] = d['class_name']
    car_relspeed_map[d['car_idx']]   = d['class_rel_speed']
```

`class_id` / `class_name` / `class_rel_speed` は**同じ `d` から同時に**書かれる。別車両の値が混ざる隙が無い。

## 反証② 同クラスGT3を「処理を要する脅威」として扱えない

**先に当方の誤りを訂正する。** 初版でこれを「並びが物理的に起きない」と書いたが、**言い過ぎだった**。
GT3が5秒後方や前方に**いる**ことは普通に起きる。実走ログにも `gapBehind:5.1` が存在する。

成立しないのは並びではなく、**その GT3 が接近警告の対象になること**である。

Yuji の指摘（2026-09-04）:

> GTP（GT3よりコースによっては10秒以上も速いカテゴリー）のほうがラップタイム早いんだよ！
> **同クラスのGT3が5秒差で近づくわけねーだろ！**（俺が順調に走っていれば）

同クラスは**ラップタイムがほぼ同じ**なので車間は詰まらない。詰まるのは自分がミスした時だけである。
さらにGTPは、自車に届く前に**その中間GT3を先に抜く**。だから「先にGT3を処理してから」という順序自体が逆である。

Codex の発話例③はこの前提の上に立つため、そのまま実装すると
**GTPの警告に、脅威でない中間車両の話が混ざる**。ドライバーが最も欲しいコールが薄まる。

### この主張の根拠はデータではない（重要）

初版で当方は「同クラスの接近率は中央値 +0.000、接近方向は1%だけ」という数字を出した。**これは根拠として撤回する。**
発見②のとおり `gapBehind` は周回に1回しか更新されない。**あの数字は固着したセンサーを測っただけである。**

**現時点で「同クラスは詰まらない」を支えているのは、Yuji のレース知識と物理であって、実測ではない。**
実測で言えるようにするには、先に発見②（GAPの更新周期）を直す必要がある。
**同クラスの接近を論じられる状態に、まだ無い。**

## 反証③ 穴はここにある — `gap_behind` にクラスの identity が無い ★核心

LLM へ渡すペイロード（`bridge.py:6677`）:

```python
'gap_behind': round(nearest_behind_gap, 2) if nearest_behind_gap is not None else None,
```

プロンプトでの提示（`prompts.js:870`）:

```js
if (live.gap_behind != null) { jp.push('後ろとのギャップ ' + live.gap_behind + '秒'); }
```

**LLM が受け取るのは「後ろとのギャップ 5.1秒」という文字列だけである。**
この値が**同クラス(GT3)の車のものだという表示が、ペイロードにもプロンプトにも無い**。

したがって GTP が接近している場面で、LLM がこの数字を GTP の GAP として答えることを
**止める仕組みが存在しない**。Yuji が報告した挙動は、この経路で成立する。

### 欠陥が2つ重なっている

1. **`gap_behind` にクラス identity が無い** — どのクラスの車の値か言えないまま LLM に渡している
2. **`gap_behind` は最大3.9分古い**（発見②）— 正しいクラスに紐付けても値自体が古い

**Codex の設計ではこれは直らない。** 要求①〜④はすべてマルチクラス選択経路（`MC fire`）に対する修正だが、
そこは既に正しい。**穴は LLM ペイロード側にある。**

### 直し方

`gap_behind` を裸の数値で渡すのをやめ、**車両 identity を伴う構造**にする:

```
gap_behind: { gap_s: 5.1, car_idx: 21, class_name: 'GT3', is_same_class: true,
              measured_at: <時刻>, age_s: 42 }
```

`class_name` があれば、LLM は GTP の質問にこの値を使えない。
`age_s` があれば、3.9分古い値を「今の値」として答えられない。

## 発見① マルチクラスの「◯秒」は接触までの時間ではない

`_mcgap = -_pd * player_last_lap` は、**自車のラップタイムで距離を秒に換算した値**である。
GTPがどれだけの速度差で迫っているかが入っていない。実走の結果:

| stage1の発話 | stage2（3秒コール）まで | 接近率 |
|---|---|---|
| 「GTP、5.7秒後方」 | **3秒** | 0.967 |
| 「GTP、6.0秒後方」 | 4秒 | 0.800 |
| 「GTP、5.9秒後方」 | 7秒 | 0.429 |
| 「GTP、5.6秒後方」 | **30秒** | 0.097 |
| 「GTP、5.8秒後方」 | **50秒** | 0.056 |

**同じ「6秒」と言いながら、実際の猶予は3秒から50秒まで17倍ばらついている。**
言葉も緊急度の段階も同一である。ドライバーには区別がつかない。

これは Codex の要求②が言う「主対象の選択」の問題ではない。**発話する数字そのもの**の問題である。
GTPが1クラスしか居ない今回のログでは、選択を直しても何も変わらない。

## 発見② 同クラスGAPは周回に1回しか更新されていない ★これが最大

依頼の範囲外だが、同じログから出た。**こちらを先に直すべきである。**

52分・559サンプル（5秒間隔）で:

| | 値が変わった回数 | 最長固着 |
|---|---|---|
| `gapAhead` | **15回** | **7.6分** |
| `gapBehind` | **14回** | **7.5分** |

`gapBehind:4.1` が**90サンプル連続＝7.5分間まったく同じ**。生きた値ではない。

### 周回更新との一致

gapBehind が変わった14回のうち、**11回が周回更新の±10秒以内**。うち**8回は誤差0秒**。

```
10:14:30  周回更新との差 +0秒     10:31:06  周回更新との差 +0秒
10:22:20  周回更新との差 +0秒     10:35:06  周回更新との差 +10秒
10:27:06  周回更新との差 +0秒     10:43:06  周回更新との差 +0秒
```

原因は `CarIdxF2Time`（`bridge.py:5312`）。レース中のF2Timeは**リーダー差**で、
**S/Fライン通過時にしか更新されない**。その差分を取っているので、車間も周回に1回しか動かない。

**Le Mans のラップは236秒。つまり「後ろとのギャップ」は最大3.9分前の値を喋っている。**

### 会話記憶Boxの訂正16件との関係（仮説・未検証）

8/30-31コーパスの訂正 #14 は、Luna「**後ろ0.0秒。**」に対しドライバーが「後ろ2.0だね。ギャップ。」と訂正した件である。
今回のログでも `gapBehind:0.0` が**50サンプル連続＝4.2分間**出ている。

**ドライバーは軸を間違えたLunaを訂正したのではなく、固着した古い値を訂正していた可能性がある。**
そうであれば、会話記憶Boxで訂正を検出・撤回しても**次に喋る値がまた古い**ので、同じ訂正が繰り返される。
**これは断定しない。#14 の当該ログでF2Time更新周期を確認する必要がある。**

## 提案する順序

Codex の設計は「クラスとGAPの紐付け」を直そうとしているが、**紐付けは既に正しい**。
実データが示す優先順位は次である。

0. **`gap_behind` にクラス identity と鮮度を付ける**（反証③）— Yuji が報告した挙動の直接の原因。
   **ここを直さない限り、マルチクラス側を何度直しても同じ発話が出る。**
1. **同クラスGAPの更新周期**（発見②）— 3.9分古い値を喋っている。影響範囲は
   GAPコール・戦略判断・デブリーフ・会話記憶Boxの訂正まで全部に及ぶ。
   `LapDistPct` ベース（マルチクラスが既に使っている経路）へ寄せれば連続更新になる。
   **マルチクラス側は5.7→2.8秒を3秒で追えており、この経路は実走で動いている実績がある。**
2. **マルチクラスの数字を接触時間にする**（発見①）— `closing_rate` を測り、
   「◯秒後方」ではなく**接近率つき**にする。17倍のばらつきが消える。
3. 要求⑤の診断 — ただし記録するのは車両IDではなく **`closing_rate` と更新時刻**。
   紐付けの証拠は既にあるが、**値が新しいかの証拠が無い**。
