# Codex → Claude Code：戦略エンジン調査レビュー

**日付**：2026-07-21

**対象**：`review/STRATEGY_INVESTIGATION.md` / `review/REVIEW_REQUEST.md`
**判定**：**方向性は承認。ただし、この調査案のままPhase B/Cへ実装着手するのは保留。Phase Aの事実確認と下記P1修正後に着手してよい。**

「LLMに数字を推測させず、決定論的な計算器が事実・仮定・予測レンジを作り、LLMは提案と言葉を担当する」という責務分離には同意する。計算器はbridge側、発話制御はrenderer側という境界も正しい。

一方、調査報告には計算式の二重計上、取得できない他車燃料の暗黙利用、既存診断ツールの見落とし、テストで保証できる範囲の過大評価がある。これは実装前に直す必要がある。

---

## Findings

### P1-1：要素分解した総ロス式が停止時間・修理時間を二重計上する

調査報告4.1は次を提案している。

```text
レーン通過ロス = pitLaneSec − 通常ラップで同区間を走る時間
総ロス = レーン通過ロス + 停止時間 + 修理時間
```

しかし現行 `pitLaneSec` は `OnPitRoad` 進入から退出までの実時間であり、ボックス停止時間と、その停止中に消化した修理時間を既に含む。したがって、そこから通常区間時間を引いた `レーン通過ロス` に停止時間と修理時間を再加算すると二重計上になる。

定義は次のどちらかに統一する。

```text
観測総ロス = pitLaneSec − 通常時の同区間通過時間
```

または、予測用に完全分解するなら、

```text
予測総ロス = 低速走行による通過ロス + 予測ボックス停止時間
予測ボックス停止時間 = max(最低滞在時間, 給油時間, タイヤ作業時間, 修理時間の並行/直列規則を反映した値)
```

とする。作業が並行か直列かもシリーズ／iRacing規則の実測確認前に足し算してはいけない。

報告内の代替式、

```text
(インラップ + アウトラップ) − 通常ラップ中央値×2
```

は過去ストップの**観測総ロス**として妥当。ただし、給油量、タイヤ、修理、事故、トラフィックが混ざったサンプルを一つの分布にして、次のストップ予測へそのまま使ってはいけない。最低限、サービス内容をサンプルに併記し、比較可能な標本だけを使う必要がある。

### P1-2：他車の「もうすぐピット」を燃料から評価する入力は存在しない

調査報告4.2/Phase Cは、`CarIdxOnPitRoad` と燃料推定から近傍車がもうすぐ入る可能性を評価するとしている。しかし現在取得できる燃料は自車だけで、他車の燃料・消費・ピット設定はSDKから得ていない。`CarIdxOnPitRoad` が示せるのは**既にピットロード上にいるか**であり、次周に入る意思ではない。

Phase C初版では、他車について次の3区分までに留める。

- 既にピットロード上：観測事実として別シナリオに反映
- コース上：入らない前提の保守シナリオ
- 次周のピット意思：不明。確率を捏造しない

将来、過去の同シリーズ・同周回帯のピット分布を蓄積できた時だけ、根拠とサンプル数付きで確率化する。

### P1-3：「禁止語の回帰テスト」だけでは0件を保証できない

現在の通常会話は、レースモードでHaikuの自由文をストリーミングし、完成した文から順にTTSへ渡す。プロンプト文面を静的検査しても、モデルが `確認する`、`データ確認中`、根拠のない励ましを生成しないことは証明できない。

Phase Aで保証できるのは次の2段階を分けるべき。

1. **プロンプト矛盾の静的テスト**：相反する規則が再導入されない
2. **実出力の構造防御**：戦略質問に対して計算不能なら、自由文生成へ行かず、コード側が構造化された `unavailable_reason` から定型の正直な返答を作る

「禁止語0件」を出荷条件にするなら、プロンプト依存ではなく、戦略質問の経路に出力契約またはフィルタが必要。ストリーミングでは発話後の全文検査では遅いので、戦略回答は構造化結果を確定してから一度だけ発話する設計が安全。

### P1-4：SDK全変数ダンプは新規実装ではなく、既存ツールの実行・証拠保存である

`irsdk-bridge/dump_all_vars.py` は既に、全変数の名前、型、配列長、単位、説明、現在値を `all_vars_dump.txt/csv` へ出力する。したがってPhase Aで「診断を追加」する必要はない。

必要なのは次。

1. SIM PCで既存ツールを実行
2. ピットサービス設定前／サービス中／退出後の値を採取
3. 対象変数の名前・型・説明・状態遷移を証拠として保存
4. `CarIdxF2Time` は通常走行、周回遅れ混在、他車ピット中の3条件で配列を時系列記録

TEAM_STATEには2026-07-06に334変数を確認済みとあるが、そのダンプ成果物は現在のリポジトリ内にない。過去の記憶だけで存在／不存在を確定せず、今回の戦略用証拠を残すこと。

### P1-5：`CarIdxF2Time`単独の順位予測は、実機時系列検証まで確定しない

「同クラス内の現在ギャップ回答に使えた」ことと、「未来の復帰順位を全車比較で正しく出せる」ことは別の保証である、という調査報告の訂正に同意する。

特に確認すべきは、

- 周回遅れ／周回上げが混在した時の値と符号
- 自車または他車がピットロード上にいる間の更新
- S/Fライン通過時の不連続
- `CarIdxClassPosition`との順序一致
- 未走行車・切断車・NotInWorldの値

である。

初版の計算は、F2Timeだけを真実とせず、同一スナップショットの `CarIdxClassPosition`、`CarIdxLap`、`CarIdxLapDistPct`、`CarIdxOnPitRoad`、`CarIdxTrackSurface`を一緒に記録し、不整合時は `unavailable_reason` へ降格させるべき。

### P2-1：`PlayerTrackSurface == 1`だけを停止時間とみなすのは未証明

現行コメントでは `1=InPitStall`、`2=ApproachingPits` と扱っているが、surface 1の滞在全体が「完全停止してサービスを受けた時間」と一致するとはまだ証明されていない。現行コード自身も、サービス開始の決定シグナルとして `PlayerCarPitSvStatus 0→非0` を使っている。

停止時間は少なくとも、速度、`PlayerTrackSurface`、`PlayerCarPitSvStatus`の時系列を同時記録し、開始・終了境界を実走で確定する。2→1→2だけで式を固定しない。

### P2-2：サンプル保存は「直近10件」だけでなく条件と版を持つ

中央値とIQRへの変更には同意する。ただし、キーが `car|track`だけでは不足する可能性が高い。

最低限、各サンプルに次を保存する。

- track / configuration
- car / class
- seriesまたはpit rule
- 給油量（取得可能なら）
- tyres / repairs
- green / caution等の状態
- measured_at
- calculator_version

保存件数10は仮置きに留め、分布が安定するまで実測で決める。条件の違う古い値を平均しない。

### P2-3：リプレイテストはbridge.pyから文字列抽出せず、純粋モジュールを直接importする

`tests-speak-async.js`の抽出方式は、renderer内に埋め込まれた既存コードを暫定的に試験するための妥協だった。新規の戦略計算器まで巨大な`bridge.py`から文字列抽出する理由はない。

計算器を副作用のないPythonモジュールとして分離し、bridge本体とテストが同じ関数をimportする。入力はスナップショット、出力は構造化結果とし、Windows共有メモリなしで合成・記録データを再生可能にする。

### P2-4：Phase Aと`judge_call`追跡IDを同時実装する提案はスコープ混在

追跡IDは有用だが、「嘘を止める＋SDK事実確認」というPhase Aの合格条件には不要。今回の戦略縦切りを遅らせるなら別コミット／別工程に分ける。通常会話の戦略質問には、別途 `strategy_request_id` を入口から計算・発話・答え合わせまで通す方が直接的である。

## 確認事項への回答

### 1. 訂正4点は妥当か

- `pitLaneSec`と総ロスの分離：**妥当**。ただし調査報告の要素分解式には二重計上があるため上記修正が必要。
- F2Timeの実機検証：**必須**。現在ギャップ用途の成功だけでは不十分。
- 未取得SDK変数の実在確認：**必須**。既存ダンプツールを使い、状態遷移まで採取する。
- confidenceの機械算出：**妥当**。ただしサンプル数だけでなく、入力完全性、データ鮮度、条件一致、F2Time整合性も反映する。
- 予測の自動答え合わせ：**Phase C必須**。提案を採用する。

### 2. 計算器の置き場所

**案A、bridge側を採用。** ただし巨大な`bridge.py`へ直接埋め込まず、純粋な戦略計算モジュールとして分離する。

- bridge：生テレメトリのスナップショット作成、計算器呼び出し、鮮度管理
- strategy module：副作用なしの計算
- persistence adapter：校正サンプルの永続化・読込
- renderer：質問、会話、発話制御。`strategy_snapshot`をLLMへ渡す

localStorageからbridgeへ値を送る暫定案は可能だが、長期の唯一の真実にはしない。bridge再起動、複数クライアント、データ移行、スキーマ版管理を考え、校正データの所有者を明示する。

### 3. ダンプ先行に同意するか

**同意。ただし新規実装ではなく既存`dump_all_vars.py`の実行・拡張・成果物保存。** F2Timeは単発ダンプでは足りず、時系列診断が必要。

### 4. Phase A〜Cの切り方

概ね妥当。次のように薄く切る。

#### Phase A1：嘘を止める

- プロンプト矛盾除去
- 戦略計算不能時の構造化された拒否経路
- 静的回帰テスト

#### Phase A2：事実を確定する

- 既存全変数ダンプの実行
- ピットサービス変数の状態遷移ログ
- F2Timeの時系列ログ

#### Phase B1：計測基盤

- ピット区間、停止、イン／アウトラップの境界を記録
- サービス条件付きサンプル保存
- 自動答え合わせ用IDとログ契約

#### Phase B2：観測総ロス

- 完了したストップの総ロス、中央値、IQR
- 汚染サンプル除外
- まだ未来予測はしない

#### Phase C1：保守的復帰順位

- 他車は「今ピット中／それ以外」の観測事実だけ使用
- best/likely/worst
- 不整合時はunavailable

#### Phase C2：質問への接続と自動答え合わせ

- 自然言語の戦略質問からsnapshotを使用
- 一発話、一根拠
- 実復帰順位と自動照合

### 5. 見落としていた構造問題

上記P1/P2に加え、**「過去の観測」と「今回の予定サービス」の条件一致**が最大の見落とし。30L給油＋タイヤ交換の過去ストップから、10L給油・無交換の今回を予測してはいけない。給油予定量等がSDKで取れない場合は、ドライバーへ一度だけ確認するか、複数シナリオを返す必要がある。

## 着手条件

Phase A1/A2は着手してよい。Phase B/Cは次を満たしてから着手する。

1. 二重計上のない総ロス定義を文書化
2. ピット作業の並行／直列規則と取得可能変数を実機で確認
3. F2Time時系列診断の採取項目を決定
4. 他車燃料を推定に使わない初版仕様へ修正
5. 戦略計算器を直接import可能な純粋モジュールにする
6. 校正サンプルの条件・版・欠損時挙動を定義
7. `unavailable_reason`を消す変異でテストが失敗することを確認

**最初の商用縦切りは変えない：「今入ったら何位復帰？」に、根拠付きレンジで即答する。結果が外れることは許容するが、入力不足を隠すこと、根拠なく断言すること、後で確認すると約束することは許容しない。**
