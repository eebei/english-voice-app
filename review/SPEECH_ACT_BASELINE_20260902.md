## 0. 測定方法を作り直した経緯（重要）

初版の抽出は `CONVO [USER]` を**単独で**切り出していた。Yuji の指摘：

> 君が疑問に思ってるのは前後の文脈をみれば解決できることばかりだよ！
> その短文だけ切り取っては本人でもわかりづらいよ。訂正などがほとんどだね。

**発話の意図は「直前に Luna が何を言ったか」で決まる。それを捨てた状態で
「軸が判定できない」と報告していたのは、測定器の欠陥だった。**
corpus を作り直し、直前 Luna 発話3件・STT信頼度を全件へ付けた。
その結果、26件あった「要判断」は5件まで減り、残りは文脈で確定した。

これは §検証水準 の受入基準④「正解を外部から取る」と同じ型の失敗である。
**測る対象から、判定に必要な情報を落としてはならない。**

## 1. 確定した分布 — 訂正が質問と同数

| 発話行為 | 件数 | 割合 |
|---|---:|---:|
| **質問** | 17 | 25% |
| **訂正** | **17** | **25%** |
| 応答（デブリーフ） | 10 | 15% |
| 報告 | 8 | 12% |
| 決定 | 5 | 7% |
| 独り言 | 4 | 6% |
| 雑談 | 3 | 4% |
| 不能（STT崩壊） | 2 | 3% |

**ドライバーは、質問と同じ回数だけ Luna を訂正している。**

| 発話行為 | 正しく扱われた | 母数 | 正答率 |
|---|---:|---:|---:|

| 質問 | 8 | 17 | 47% |

| 答えるべきでない発話（報告・独り言・雑談・不能） | 誤発火 1 | 17 | — |

`measurement_disputed`（訂正を扱う唯一の経路）は **実走4本で発火0件**。

## 4. この基準線から言えること

**当方が測ろうとしていた「質問軸の一致率」は、問題の半分でしかなかった。**
軸を当てる前に**発話行為を取り違えている**。訂正0%は軸の問題ではない。

Codex の `speech_act` / `fact_axis` 2軸分離は、この実測で裏付けられた。
ただし当方が挙げた `speech_act` は5種だったが、実データは **9種**を要求する
（質問・訂正・応答・報告・決定・独り言・雑談・不能・依頼）。

**設計変更の合否は、この表の数字が上がったかどうかで判定する。**
特に **訂正 0/17** が動かない案は、何が改善しても採用しない。

## 7. 原本ログの提供と、実名のログ出力停止（2026-09-02）

Codex が独立採点に原本を要求したため repo へ入れる準備をしたところ、
**このリポジトリは public** であり、診断ログに **他ドライバーの実名が72人分**入っていた。

```
DRIVER idx=0 #923 'Damien Mcbay' LIC=19.307(SR 3.07) iR=2715
```

iRacing は本名表示のため、これは実在の個人名とレーティングである。
当方のMDに subsession ID `88367382` を記載しているので、名前が無くても照会で特定できる状態でもあった。
**commit 前に停止し、Yuji へ報告した。**

### 対応1: `bridge.py` の診断ログから実名を落とした

`irsdk-bridge/bridge.py:2788` の `DRIVER` 行は idx / car_number / SR / iRating の
**紐付けを追う目的**であり、実名は判定にも照合にも使っていない
（危険ドライバー判定は `iRating <= 1300` / `SR 1.0-2.0` のみ、
`car_name_map` は指名ライバル照合用で telemetry 側。ログにも発話にも出ていない）。

名前の出力を削除した。**機能は不変。** 診断ログはテスターから送られ共有されるため、
今後まーぼー・八木両氏のログにも他人の実名が入らない。

### 対応2: 伏せ字版を repo へ入れた

`review/corpus/raw/*-redacted.log`（4本・3.8MB）。
実名 **105箇所**を `<redacted>` へ置換し、置換後に実名が残っていないことを機械確認した。
それ以外（発話・経路・回答・タイムスタンプ・SR・iRating・car number）は無加工。
訂正17件の独立採点に必要な情報は全て残っている。

**SR と iRating は残した。** 危険ドライバー判定の根拠であり、
名前と切り離せば個人の特定には至らないと判断した。**この判断に異論があれば伏せる。**

### 対応3: 同一ドライバーの識別キーは `cust_id`（実名ではない）

対応1で実名をログから外した後、Yuji から技術的な指摘があった。

> だったら名前が必要だ、SRもiRatingもレースごとに変化するだろ？

**正しい。SR も iRating も識別子にならない。** car number もセッション内で再割当されるため固定ではない。
同じドライバーを次のレースで見つけるには固定キーが要る。

ただし**実名も識別子として弱い**。実走ログの実データにその証拠がある。

```
'Rodrigo Suarez4'  'Thomas Stewart10'  'Michael Strickland4'  'Niklas Swierczyk5'
```

末尾の数字は **iRacing が同名ドライバーを区別するために付けたもの**である。
表示名は衝突し、改名もできる。

| キー | 一意 | 安定 | 備考 |
|---|---|---|---|
| SR / iRating | ✗ | ✗ | レースごとに変化 |
| car number | ✗ | ✗ | セッション内で再割当 |
| 表示名 | △ | △ | 同名衝突（実データで確認）・改名可能 |
| **`cust_id`** | **✅** | **✅** | 公式リザルトの正本 |

公式リザルト `eventresult-88367382.json` でも `cust_id` が正本で、`display_name` は表示名である。

```
cust_id = 1428687   display_name = Dmitriy Laptiyov
```

### 現状の欠落

`bridge.py` の DriverInfo パーサーが読むのは
`LicLevel` / `LicSubLevel` / `UserName` / `CarNumber` / `IsSpectator` / `CarIsPaceCar` / `CarClassID` のみ。
**`UserID`（= cust_id）を読んでいない。取れるはずのものを取っていない。**

したがって現在の危険ドライバー判定は**セッション内限定**であり
（`iRating <= 1300` または `SR 1.0-2.0` をその場で判定するだけ）、
次のレースへ持ち越す仕組みは存在しない。

### 決定事項（Build 290 の記録と一致）

Build 290 で既にこう決めている。

> 名前だけの永久ラベルは誤認・同名・訂正不能のため追加しない。
> 実装する場合は本人申告 → iRacing customer ID 照合 → 確認 → 期限 → 訂正／削除まで一単位とする。

**この方針を維持する。**

1. 識別キーは `cust_id`。実名は使わない
2. ログには `cust=1428687` を出す。実名は出さない
3. 実名は telemetry 内に留め、**ログ・保存・発話へは出さない**
4. 持ち越し記憶を作る場合は、Build 290 の条件（本人申告・確認・期限・訂正／削除）を満たしてから

**これで「同じ人を次のレースで見つける」要求を満たしつつ、流通するログに実名が載らない。**
プライバシーと正確性が同時に改善する（実名より `cust_id` の方が誤認しない）。
