# 第1部：GAP の identity 問題（そちらの指摘の適用先）

## 1-1. マルチクラス経路は既に原子的（反証）

`bridge.py:5738` の候補ループ:

```python
_mcls = car_class_map.get(_mi, -1)
if _mcls == -1 or _mcls == player_class_id or _mrel <= player_rel_speed:
    continue                      # ← 同クラス(GT3)はここで全部落ちる
...
_cn = _norm_class_name(car_class_name_map.get(_mi)) or 'faster class'
_mc_groups.setdefault(_cn, []).append(_mcgap)   # ← 名前もGAPも同じ _mi
```

供給元も同一レコードから同時に書かれる（`bridge.py:2884-2890`）:

```python
for d in info.get('drivers', []):
    car_class_map[d['car_idx']]      = d['class_id']
    car_class_name_map[d['car_idx']] = d['class_name']
    car_relspeed_map[d['car_idx']]   = d['class_rel_speed']
```

**実走でも0件。** MC fire 全15件すべて GTP 単独、発話は 5.6〜6.0秒。
（Yuji の「5秒」は**例示であって実測値ではない**。当方は当初これを実測と誤解し、
ログで該当秒数を探し続けた。**その探索は無駄だった。**）

## 1-2. ★穴はここ — `gap_behind` にクラスの identity が無い

LLM へのペイロード（`bridge.py:6677`）:

```python
'gap_behind': round(nearest_behind_gap, 2) if nearest_behind_gap is not None else None,
```

プロンプトでの提示（`prompts.js:870`）:

```js
if (live.gap_behind != null) { jp.push('後ろとのギャップ ' + live.gap_behind + '秒'); }
```

**LLM が受け取るのは「後ろとのギャップ 5.1秒」という文字列だけ。**
**この値が同クラス(GT3)の車のものだという表示が、ペイロードにもプロンプトにも無い。**

GTP 接近中にこの数字を GTP の GAP として答えることを**止める仕組みが存在しない**。

## 1-3. さらに、その値は最大3.9分古い

52分・559サンプル（5秒間隔）で:

| | 値が変わった回数 | 最長固着 |
|---|---|---|
| `gapAhead` | **15回** | **7.6分** |
| `gapBehind` | **14回** | **7.5分** |

gapBehind の変化14回中、**11回が周回更新の±10秒以内（8回は誤差0秒）**。

原因は `CarIdxF2Time`（`bridge.py:5312`）。レース中の F2Time は**リーダー差**で、
**S/Fライン通過時にしか更新されない**。**Le Mans は1周236秒 → GAPは最大3.9分前の値。**

対照的に、**マルチクラス側は `LapDistPct` ベースで 5.7→2.8秒を3秒で追えている**。
連続更新できる経路は既に実走で動いている実績がある。

## 1-4. 提案（そちらの形をこちらへ適用する）

```
gap_behind: { gap_s: 5.1, car_idx: 21, class_name: 'GT3', is_same_class: true,
              measured_at: <時刻>, age_s: 42, source: 'f2time' | 'lapdistpct' }
```

- `class_name` があれば、LLM は GTP の質問にこの値を使えない
- `age_s` があれば、3.9分前の値を「今の値」として断定できない
- 供給元を `LapDistPct` へ寄せれば `age_s` が数秒になる

## 1-5. マルチクラスの「◯秒」は接触時間ではない（別件・実在）

`_mcgap = -_pd * player_last_lap` は自車ラップで距離を秒換算した値で、速度差が入らない。

| stage1発話 | stage2（3秒コール）まで | 接近率 |
|---|---|---|
| 「GTP、5.7秒後方」 | **3秒** | 0.967 |
| 「GTP、5.9秒後方」 | 7秒 | 0.429 |
| 「GTP、5.6秒後方」 | **30秒** | 0.097 |
| 「GTP、5.8秒後方」 | **50秒** | 0.056 |

**同じ「6秒」で猶予が17倍違う。** 言葉も段階も同一でドライバーには区別できない。
そちらの要求②（`closing_rate`）は**選択のためではなく、発話する数字のために必要**である。

## 1-6. そちらの必須再生テストへの評価

| ケース | 判定 |
|---|---|
| A / B（GT3◯秒・GTP◯秒 → 主発話GTP） | **常に緑になり何も検出しない**（同クラスは候補に入らない） |
| C（接近率が負→発話しない） | **既に実装済み**（`evaluate_multiclass_approach`）。回帰用として有効 |
| D（候補順序の入替で不変） | 有効 |
| E（class map 変異） | **有効。残すべき。** ただし `car_class_map`(ID) と `car_class_name_map`(名前) を**別々に**壊す2種が要る |

**追加すべき:**

- **F: GAPの鮮度** — 5分更新の無い値を事実として答えない（`unavailable` か「◯分前の値」と明示）
- **G: 接近率の伝達** — 0.056 と 0.967 で**発話が区別される**こと
- **H: identity** — `gap_behind` を GTP の質問への回答に使えないこと

# 第2部：本題 — 「ピットは◯周目」を記憶から出す

Yuji の要求（こちらが主題）:

> Lunaに「何周目にピットイン？」と持ちかけて、ここで即回答が欲しかった。
> **記憶装置が作動すれば、次のレースで学習した燃料消費量をスタート前に会話でき、
> 「ピットインは6周目になるよ」と発話できるようになっていることが大切。**
> 対症療法ばかり上塗りするな！根本を探せ！

## 2-1. この日の実際のやり取り

```
10:16:42 Driver「プランa！何週目？」
10:16:43 Luna  「Plan Aはベースライン。現在の基準案。」  intent=plan_status
10:20:52 Driver「ルナ この週で入るの？それとも次の週？」  ← 4分後に聞き直し
10:20:53 Luna  「ステイアウト。次の給油目安はあと1周。」  intent=pit_decision
```

1回目は**周回を答えていない**。2回目は答えたが**相対値**であって「◯周目」ではない。

## 2-2. 材料は既に全部ある

| Lap | 残燃料 | 消費 |
|---|---|---|
| 1 | 52.3L | — |
| 2 | 44.3L | 8.00L |
| 4 | 27.5L | 8.10L |
| 6 | 11.8L | 7.80L |
| 7 | 4.3L | 7.50L |
| 8 | 45.1L（給油） | — |

**実測平均 7.87 L/周**（11周・7.5〜8.1で安定）。

```
52.3L ÷ 7.87 L/周 = 6.6周 → 7周目でピット
実際のピット = 7周目   ← 一致
```

## 2-3. 根本① 記憶が「語る事実」で止まり「計画」にならない

保存済み（`renderer.html:6452` `avgFuelPerLap`）、読み戻し済み（`session-memory.js:161`）。
しかし読み戻した先は:

```js
bits.push(`平均${facts.avgFuelPerLap.toFixed(2)}L/周`);   // 「前回…平均7.87L/周。」
```

**思い出を語る一文を作るだけ。ピット周回の計算に入る経路が無い。**
「あと1周」しか言えないのは、その場の残燃料からしか計算していないため。
**記憶の燃費 × グリッドの搭載量、この掛け算が存在しない。**

## 2-4. 根本② 問いの一部だけで intent を決め、残りを捨てる

`engineer-card.js` の判定順:

```js
158:  PIT_DECISION  … 周回を問う語は すべて "ピット/ボックス" とセットの時だけ一致
160:  PLAN_STATUS   … 「プラン\s*[ABCＡＢＣ]」で一致   ← 「プランa」がここに掛かった
```

**「何周目？」に独立したパターンが無い。** 周回を問う語は "ピット" の修飾としてしか登録されていない。

`local-intent-router.js:204` も `engineer-card.js` も **`if (regex.test) return` の一本道**。
**先に一致した1つを返して終わる。**

## 2-5. 設計：グリッドに仮説を持って現れる

現在は**実測を待ってから初めて答える**（3クリーンラップ必要）。
あるべきは**仮説を持って現れ、実測で更新する**。

| 段階 | 出所 | 言い方 |
|---|---|---|
| グリッド | 記憶（前回実測） | 「前回7.9だったから**7周目の計画**。3周で見直す」＝**推定と明示** |
| 3周後 | 今日の実測 | 差し替え。**計画が変わらなければ短く確認だけ** |
| 以降 | 今日の実測 | **計画が変わった時だけ**発話 |
| 記憶なし | — | 「初めてだから3周走らせて」＝**捏造しない** |

```
pit_lap_plan: { lap: 7, basis: 'memory_previous' | 'measured_today',
                confidence: 'estimate' | 'measured',
                fuel_start_l: 52.3, burn_l_per_lap: 7.87, sample_laps: <n> }
```

**`basis` を必ず持たせる。推定を実測として喋らせない唯一の防波堤。**

## 2-6. intent の並列化（Yuji 判断）

当方は当初「独立パターン1本追加で済ませ、複合分解は別課題」を推奨した。
根拠は「実走17件中、複合は1件」。**この根拠は弱く、撤回した。**
17件は Yuji 1人・1レースの標本であり、しかも**その1件は失敗している**（失敗率100%）。

Yuji 判断:

> 尋ね方（質問）はDriverによって変わってくるから、**複数を並列に並べて反応させる**ようにしたほうがいい

**本質はここ。** 欠陥は複合質問ではなく、
**一部だけ一致したのに全部を理解したかのように断定して答えること**である。
「プランa！何週目？」は `plan_status` が **confidence 0.96** で掴んで確定させた。

### 影響範囲

| | 判定経路 |
|---|---|
| `local-intent-router.js` | **34** |
| `engineer-card.js` | **31** |
| 計 | **65** |

### リスクを閉じ込める並列化

```
1. 全パターンを評価し、一致を全部集める（最初で止めない）
2. 一致が1つ     → 今と完全に同じ経路。挙動は変わらない
3. 一致が2つ以上 → 両方に答える
4. 未回答部分が残る → 断定せず、決定論的な事実を添えて LLM へ渡す
```

**②が安全装置。** 既存65本は「1つだけ一致」でしか発火しないため**構造上退行しない**。
挙動が変わるのは**今まさに誤答している質問だけ**。
**④が「尋ね方が変わる」への答え** — 想定外の言い回しは掴まずに LLM へ渡す。

# 第3部：Codex への依頼

## 3-1. 反証してほしい点（当方の主張を疑う順）

1. **`gap_behind` の identity 追加が、既存の GAP 回答を壊さないか。**
   `prompts.js:870` は多くの回答が通る経路である。構造体化の影響範囲を独立に測ってほしい。
2. **`age_s` を持たせた時、「古い」の閾値は何秒が妥当か。**
   当方は決めていない。F2Time が周回更新である以上、

   「一致が1つなら同じ」が成り立たない経路（副作用を持つ intent、状態を変える intent）が
   65本の中に無いか。当方は網羅確認していない。
4. **記憶の燃費をどこまで条件一致させるか。**
   現在 `matchesIdentity` は 車種×コース×ドライバー を要求。
   **路面温度差・セットアップ差をどう扱うか未決。** 温度が10℃違えば燃費は変わる。
