# Local Processing vs Current PITWALL — Independent Review Request

作成日: 2026-09-02 JST  
依頼先: Claude Code（独立検証）  
対象: Build 292 / commit `39a4386` と、次期V4候補設計

## 目的

ローカル処理を採用すれば必ず改善する、という前提を置かず、現行PITWALLと比較して検証する。
Codexは今回、GAP・燃料・順位・周回数などをローカル計算＋定型応答へ寄せる案を提示した。
この判断が本当に、速度・コスト・正確性・会話品質・運用性の面で現行構成を超えるのかを、Claudeが反証可能な形で評価する。

## 用語の整理

- **現行構成**: Bridge/iRacingデータ → renderer/ルーター → 必要に応じてLLM（Luna） → TTS
- **ローカル処理**: 確定済みのテレメトリ事実をPC内で計算し、固定契約の回答を返す処理
- **LLM処理**: 文脈理解、複数要因の比較、戦略判断、自然な説明、デブリーフをLunaが行う処理
- **RaceLab/RaceWise系データ**: 全車順位、ラップ、ピット周期など、外部オーバーレイが表示・推定する情報。取得可能性と権威性を別々に検証する

## 比較対象

| 観点 | 現行PITWALL | ローカル事実回答 | ハイブリッド案 |
|---|---|---|---|
| GAP/燃料/順位 | LLMへ渡る場合、遅延・取り違え・話題逸脱の余地 | 高速・定型・数字創作を抑制 | 事実はローカル、意味づけはLuna |
| 戦略 | 文脈を扱えるが根拠の固定が弱い場合あり | 複雑な比較は不得手 | 計算結果をLunaへ渡し一つの推奨を出す |
| コスト | LLM/API使用量が増えやすい | API呼び出しを削減可能 | 必要箇所だけLLMへ送る |
| レイテンシ | ネットワーク・キューの影響 | 原則低い | 緊急系は低遅延、判断系は許容遅延 |
| データ欠損 | LLMが推測・別回答へ流れる危険 | 事実がなければ回答不能 | 確定/推定/未成立を分ける必要 |
| 更新性 | プロンプト修正で対応しやすい | コード更新が必要 | 契約と計算をテストで固定 |
| 誤りの影響 | 誤った説明を生成する可能性 | Bridgeの誤値を高速に増幅する危険 | ソース・時刻・対象車の検証が必須 |

## 必ず検証する危険性

ローカル処理はLLMの嘘を減らせる一方、入力が誤っている場合に誤情報を高速かつ断定的に増幅する。
Claudeは次をコードとログで確認すること。

1. `gap_behind` が本当に直後車両の値か（前後・クラス・対象車の取り違えがないか）
2. 値の観測時刻、セッション、対象car_idxが発話時点と一致するか
3. stale値、null、0、空文字が確定値へ化けないか
4. GTP/GT3混走で総合GAPとクラスGAPを混同しないか
5. Fuel Windowの状態と、単なる燃料不足警告を混同しないか
6. ローカル回答がLunaの戦略判断を不正に上書きしないか
7. ローカル処理の定型文が、自然な質問に対して機械的・不自然にならないか
8. RaceLab/RaceWise由来の推定値をiRacingの確定値として扱っていないか
9. Bridgeが誤値を出した場合、誤答がLLM経由より増幅されないか
10. 通信断・セッション切替・再接続時に古い回答が発話されないか

## 性能・コスト比較で提出する数値

推測ではなく、同じ入力を使った測定値を記録する。

- ルーター入口から画面表示までのレイテンシ（p50/p95）
- ルーター入口からTTS開始までのレイテンシ（p50/p95）
- LLM呼び出し回数（1レースあたり、質問別）
- 1レースあたりの入力・出力トークンまたは推定API費用
- ローカルCPU・メモリ使用量
- データ欠損時の誤答率、無回答率、適切な説明率
- GAP/燃料/順位/周回数の正答率
- 無関係回答、話題逸脱、「了解」だけで終了する割合

## 受入条件

ローカル処理の採用は、次を満たした場合だけ承認する。

- 対応対象の事実質問で、実走または再生ログの正答率が90%以上
- 誤った数値を断定するケースがゼロ
- 入力が誤っている場合に、ソース・時刻・対象の不一致を検出できる
- LLM呼び出し削減量とレイテンシ改善を実測で提示できる
- ローカル回答が戦略相談を奪わず、Lunaの判断へ正しく引き渡される
- データ不足時に「その数値は確認できない」だけで終わらず、理由と次の行動を返す
- 現行構成より会話品質が悪化しない
- Windows実機・iRacing実走で同じ契約が再現する

## Claudeへの依頼事項

1. `39a4386` の差分と現行の回答経路を独立確認する
2. ローカルルーターの全分岐（GAP、燃料、順位、周回、ピット、天候）を列挙する
3. 各分岐について、入力の権威性・鮮度・対象識別・発話出口を確認する
4. 現行PITWALLより悪化する可能性を最低3点挙げる
5. ローカル処理へ移すべき項目、Lunaへ残すべき項目、保留すべき項目を分類する
6. 上記の性能・コスト・正答率を測る再現可能なテストを追加する
7. 受入条件を満たさない場合は「採用不可」と明記し、代替案を出す
8. 検証結果を `review/LOCAL_PROCESSING_INDEPENDENT_VERIFICATION_20260902.md` に記録する

## 判断の原則

ローカル処理は目的ではない。目的は、ドライバーが必要な時に、正しい事実と役に立つ判断を自然に聞けること。
コストが下がっても誤答が増えるなら不採用。速度が上がっても誤ったGAPを断定するなら不採用。
最終的には、**現行PITWALLとの実測比較で改善が証明された部分だけをV4へ採用する**。
