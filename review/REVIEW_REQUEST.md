## 2. 技術的に訂正したい点（提案書への反論を含む）

### ① `pit_lane_sec` と「ピット総ロス」の混同

`bridge.py` は既に**ピットレーン進入→退出の所要時間**を実測し、`pw_ctmem` に保存している（✅コードで確認）。
しかし復帰順位に必要なのは**「入らなかった場合との差」**であり、別物：

```
総ロス = (インラップ + アウトラップ) − (通常ラップ中央値 × 2)
```

提案書の Phase B は正しく「通常ラップとピット通過ラップの差」と書いているが、
**出力契約の `total_loss_s` と既存の `pitLaneSec` を同一視すると計算が壊れる**。定義の分離を明示したい。

### ② `CarIdxF2Time` を復帰順位に使う前に実機検証が必要

同クラス内のギャップ用途では実走で正しく機能している（✅）。
しかし復帰順位計算は**全車の総経過時間順序**として使うことになり、要求が一段厳しい：

- **周回遅れ／周回上げの車**が混在する時、単純な大小比較で順位が出るか
- **ピット中の車**の F2Time はどう振る舞うか（凍結／増加）

**ここを推測で実装すると、昨日の LapDistPct 符号反転と同種の事故になる。**
あなたが F2Time の挙動について既知の情報を持っていれば教えてほしい。無ければ実機で確定させたい。

### ③ 提案の入力リストに、現在取得していない変数がある

「給油予定量」「給油レート」「タイヤ交換の有無」「ボックス最低滞在時間」は**未取得であり、SDKに存在するかも未検証**。
提案書はこれらを所与としているが、**実在確認が先**だと考える。

### ④ 信頼度は実測ばらつきから機械的に出すべき

`"confidence": "medium"` を人手のルールで決めると、また「それっぽいが根拠のない値」になる。
**ピットロスの実測分布とサンプル数から導出**し、3サンプル未満は `low` 固定を提案する。

### ⑤ 提案に無いが必要だと考える点：予測の自動答え合わせ

提案書7節の検証条件は手動集計を想定しているように読めた。
**予測を出した時点でログに刻み、実際の復帰順位が判明した時点で自動照合して記録する**仕組みを、Phase C に含めたい。
これが無いと精度が上がらず、Phase E（アンダーカット）の土台も育たない。

## 4. ★あなたの判断を仰ぎたい：計算器をどこに置くか

**未決事項。** 校正データ（`pitLaneSec`）は **renderer の localStorage** にあり、
テレメトリの生値・鮮度・ポーリング周期は **bridge** が持っている。

- **案A：計算器を bridge に置く**（renderer が接続時に校正値を送る）
  - 理由：`strategy_snapshot` は発話系よりデータ側に近い。鮮度（`valid_for_s`）を正しく扱えるのは bridge
- **案B：計算器を renderer に置く**（校正値が手元にある）

**私の推奨は案A**。ただしこれは、あなたが先日指摘した
**「発話状態は renderer にしかない」問題と対称の構造**であり、同じ轍を踏みたくない。

また現状の校正保存には欠陥がある：
**`pitLaneSec` が「過去との平均」（`(prev+new)/2`）で保存されており、ばらつきが失われている。**
あなたの要求する「中央値とばらつき」を満たさないため、**サンプル配列での保存に変更**したい。

## 5. ★着手順の変更提案：Phase A の最初に「SDK全変数ダンプ」

上記 #2-③ の未検証項目が全て「**SDKに在るのか無いのか**」であり、
**推測で設計すると計算式ごと作り直しになる**。

`find_var` は既に変数ヘッダを走査しているので、**全変数名＋型を1回ダンプする診断**を入れれば、
**1回の走行で全て確定**する。これを Phase A の先頭に置きたい。

昨日、LapDistPct の符号を「物理的にこうだろう」と推測したまま出荷し、
**迫る車を捨てて抜かれた車を警告する**状態を実走まで気づけなかった。同じ過ちを避けたい。
