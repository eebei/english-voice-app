## 1. 提案への賛否と、技術的に誤っている点

### 賛成（設計の芯は正しい）

**「LLM に数字を計算・推測させない。計算器が出した根拠から、どれを勧めるかと伝え方を担当させる」**——これは今日までに繰り返し実証された失敗パターンの根絶になる：

- 燃料の「92L / 200L」トンチンカン → **LLM に暗算させていた**
- 「あと何周？」に答えられなかった → **残り周回の計算器が壊れていた**（型誤読）
- 「確認する」の連発 → **答えを持たないまま喋らされていた**

**計算できないなら「無い」と言う**という契約も正しい。今日、燃料で「不明を"あと1周"に変換しない」という同じ原則を採用済み。

### 技術的に訂正が必要な点（4件）

#### ① `pit_lane_sec`（実測済み）は「ピット総ロス」ではない ⚠️重要

現在 `bridge.py` が測っているのは**ピットレーン進入→退出の所要時間**（✅実装済・後述）。
しかし復帰順位に必要なのは**「入らなかった場合との差」**であり、両者は別物：

```
総ロス = (インラップ + アウトラップ + 停止時間) − (通常ラップ × 2)
```

提案書の Phase B は「通常ラップとピット通過ラップの差を記録」と**正しく書かれている**が、
出力契約の `total_loss_s` と既存の `pitLaneSec` を**同じものとして扱うと計算が壊れる**。
定義を明示的に分離すべき。

#### ② `CarIdxF2Time` の意味を、復帰順位計算に使う前に検証すべき ⚠️

現在 `standings_gaps` で「レース中は**リーダーからの遅れ**」として使用しており、同クラス内のギャップ回答は実走で正しく機能している（✅）。
しかし復帰順位計算は**「全車の総経過時間順序」として使う**ことになり、要求が一段厳しい：

- 周回遅れ／周回上げの車が混在する時に、単純な大小比較で順位が出るか
- ピット中の車の F2Time がどう振る舞うか（凍結するか、増え続けるか）

**この2点は実機で確認してから計算式を確定すべき**。ここを推測で作ると、今日の「前後逆転」と同種の事故になる。

#### ③ 提案の入力リストには、現在**読んでいない**変数が複数ある

「給油予定量」「給油レート」「タイヤ交換の有無」「ボックス最低滞在時間」は現状取得していない（後述3節）。
**SDK に存在するかどうかも未検証**。提案書はこれらを所与としているが、**実在確認が先**。

#### ④ 信頼度（confidence）は実測ばらつきから導くべき

`"confidence": "medium"` を人手のルールで決めると、また「それっぽいが根拠がない値」になる。
**ピットロスの実測分布（中央値と幅）と、近傍車のピット可能性から機械的に算出**すべき。
サンプル数が閾値未満なら `low` 固定、が最も正直。

### 提案に無いが必要だと考える点

**「予測を必ず答え合わせする」仕組み**。提案書7節の検証条件は手動集計を想定しているが、
**予測を出した時点でログに刻み、実際の復帰順位が出た時点で自動照合して記録する**べき。
これが無いと精度が上がらず、Phase E（アンダーカット等）の土台も育たない。

## 4. ピット総ロスと復帰順位をどう計算するか

### 4.1 総ロス

```
停止時間     = ボックス到達〜発進（PlayerTrackSurface 1 の滞在時間）
レーン通過ロス = pitLaneSec − (通常ラップでその区間を走る時間)
給油による延長 = max(0, 給油量 / 給油レート − 他作業時間)
総ロス       = レーン通過ロス + 停止時間 + 修理時間
```

**実務上より頑健な代替**（Codexの Phase B と同じ）：
```
総ロス = (インラップ + アウトラップ) − (通常ラップ中央値 × 2)
```
こちらは**個別要素を知らなくても1つの数字で測れる**。まずこちらで校正し、
給油量等が取得できたら要素分解に進むのが安全。

### 4.2 復帰順位

`CarIdxF2Time` が「リーダーからの遅れ」であることを利用する：

```
自分の予測F2Time = 現在のF2Time + 総ロス
復帰順位 = (予測F2Timeより小さいF2Timeを持つ同クラス車の数) + 1
```

**best / likely / worst の作り方**：
- `likely` … 総ロスの**実測中央値**を使う
- `best`  … 中央値 − ばらつき、かつ**近傍車がピットに入る**ケース
- `worst` … 中央値 + ばらつき、かつ**近傍車が入らない**ケース

**近傍車の扱いが精度を決める**：復帰位置の前後3〜4台について、
`CarIdxOnPitRoad` と燃料推定から「もうすぐ入りそうか」を評価する。

### 4.3 前提の明示

出力には**必ず仮定を添える**（提案書4.2に同意）：
「18L給油・タイヤ無交換・修理無し」という仮定が変われば答えが変わるため。

## 5. コースごとのピットロスをどう実測・保存するか

### 現状（✅一部実装済）
`pw_ctmem[car|track].pitLaneSec` に保存。ただし：
- **保存が「過去との平均」**（`(prev+new)/2`）＝**ばらつきが失われる**。Codex要求の「中央値と幅」に不足
- **localStorage（renderer）にあり、bridge から読めない**

### 提案する変更

1. **サンプルを配列で保持**（直近10件程度）し、**中央値と四分位範囲**を出す
2. **総ロス（インラップ+アウトラップ方式）も併せて記録**——これが本命の値
3. **アーキテクチャの決定が必要**：
   - **案A**：計算器を bridge に置き、renderer が接続時に校正値を bridge へ送る
   - **案B**：計算器を renderer に置く（校正値が手元にある）
   - **私の推奨は案A**。理由：テレメトリの生値・鮮度・ポーリング周期は bridge 側が持っており、
     `strategy_snapshot` は発話系より**データ側に近い**。校正値の受け渡しは既存の `cmd` 経路で足りる。
   - ただし**この判断は Codex の意見も聞きたい**（発話状態が renderer にある件と対称の問題）

### 汚染の防止
- インラップ／アウトラップは**燃料学習から既に除外済**（`pit_this_lap`）。同じ考え方でロス計測にも

## ⚠️ Codexレビューによる訂正（2026-07-21・実装前に修正）

### 訂正1：総ロスの要素分解式が二重計上していた（P1-1）

本報告4.1に書いた式は**誤り**：
```
✗ 総ロス = レーン通過ロス + 停止時間 + 修理時間
```
`pitLaneSec` は `OnPitRoad` 進入→退出の実時間であり（✅コードで確認）、**ボックス停止時間も、その間に消化した修理時間も既に含んでいる**。そこから通常区間時間を引いた値に停止・修理を再加算すれば二重計上になる。

**正しい定義（どちらかに統一する）**：
```
観測総ロス = pitLaneSec − 通常時の同区間通過時間
      または
予測総ロス = 低速走行による通過ロス + 予測ボックス停止時間
  ※予測ボックス停止時間 = 最低滞在/給油/タイヤ/修理の**並行か直列か**を実測で確認してから決める

```
